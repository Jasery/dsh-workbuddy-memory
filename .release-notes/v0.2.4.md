# v0.2.4 — 路径在创建之前也要有唯一身份

两个与路径规范化有关的修复，外加项目的 CI。

## 记忆目录里「还不存在」的文件现在也拦得住了

守卫判断「这是不是记忆文件」，靠的是把目标路径和记忆目录都做一次 `realpath` 再比对。问题是 `realpath` 只对**已经存在**的路径有效：一个即将新建的文件拿不到真实路径，就保留了调用方的写法，于是永远匹配不上已经规范化过的父目录。

后果不是理论问题：`write` 可以直接在记忆目录里造出一个新文件而完全绕过 `memory_*` 工具——没有锁、没有 revision 比对、没有备份。而这恰好是守卫存在的意义：写第一条日记、写一个新的主题文件，都是「文件还不存在」的形态。

现在路径解析会找到最近的、已存在的祖先目录，再把缺失的尾段接回去。同一个文件在创建前后只有一个身份。

## 重放同一个 `operationId` 重新返回 `duplicate`

操作指纹哈希的是规范化后的路径，用的是同一条规则。所以同一个 `operationId`：第一次调用时文件还不存在，指纹用调用方写法；写入创建文件之后重放，指纹用真实写法。两者不等，重放被判成 `operation_mismatch`——回执本该提供的重放安全性就这样静默丢了，调用方会以为「这个 id 被用于别的操作」，而不是「这次写已经成功过了」。

两处现在共用同一份实现（`fslock.js` 的 `resolveLink()`），守卫的 `canon()` 直接复用，不会再各自漂移。

## 为什么以前没发现

这两个 bug 都不是 Windows 专有，只是在「临时目录本来就规范」的机器上看不出来。本机 `TEMP` 是 `C:\Users\admin\AppData\Local\Temp`，怎么写都一致；CI 的 Windows runner 用的是 8.3 短名 `C:\Users\RUNNER~1\AppData\Local\Temp`，同一个文件在创建前后就有两种写法。

换句话说：**这条 CI 上线第一天就抓到了两个真实缺陷**，包括一个让写入守卫形同虚设的。
