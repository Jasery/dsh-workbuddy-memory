一分钟读懂

插件像一本共用记事本。原方案想把它的按钮、裁剪和安全保护补齐，这个方向对；但有些问题原本已经测过，有些修法只补了外壳，有些功能加完也解决不了真正的问题。

这轮不再把所有项目都说成“保留、以后评估”。配置、写链、读取、会话快照、诊断、测试和 CI 要做；工具前缀、静默预设名单、多目录自动发现、独立重整命令与固定七天冷却，本轮明确不做。需要的整理能力并入已有读写与真实确认流程。

最先修的不是多加一个功能，而是让已有开关真的生效、相同写请求不会重复、备份不会撞名、归档不会越过预览。随后再接默认分层，减少长期携带的无关内容。

O-01 · 改后做：把裁剪改成可靠的选择与补读

原判断哪里不对

已有章节的追加发生在章节末尾，而非文件末尾。实测新条目处于全文偏移 37，文件 864 字，尾部 120 字没有它。尾截不能保证新内容可见；“最新”也不等于“必须遵守”。

预算单位也没闭合：配置 20，含 emoji 的真实注入为 75 个 UTF-16 码元；现有 truncateChars 按码点截、其余代码常用 string.length，再加标题和说明超出。工具全文分支 slice 还会留下半个代理对。超过 2 MiB 的工具读取会按截过的片段算 revision，未暴露该字节截断，后续 CAS 将对不上完整文件。

具体怎么做

  1. 分层路径按已明确核心选择，先预留规则、标题、告警与目录，再保留完整条目；所有实际输出算入同一预算单位。沿用 JS string.length 作为明确的 UTF-16 码元单位，不能叫 token 或汉字数。
  2. 全文／待划分兼容路径保留从头开始的确定性读取，但至少按完整条目或完整文本行裁剪，标明仍有后文；不新增注入裁剪方向开关。普通读取默认顺序不突然翻转。
  3. 给 memory_read 增加可选 offset（相对所选全文或章节的码元偏移）与 nextOffset，保持默认调用兼容；Unicode 边界对齐。全文与章节都返回明确 truncated、实际区间；给目录保留 sectionsOnly。
  4. revision 必须对应完整原文。超出安全读取上限时返回 too_large、revision:null、writable:false，不能把半份原文的 hash 当成整份。保守拒绝整档改写；读取片段也不能冒充完整编辑依据。
  5. 规则使用完整精简模板，低于最小模板预算则明确拒绝该配置或不注入并告警，不用静默裁剪让安全提示消失。零预算直接关闭块。

不做：head/tail 额外设置、按最近写入自动提权、HTML 注释全部免费保留。

验收：前部章节新增、长条目、emoji、0 预算、目录溢出、分页拼接、超字节上限均有断言；配置额度等于实际贡献硬上限，读取不能返回伪完整 revision。

证据：章节追加、字节裁剪、码点计数、输出包装、读取与 revision。验证脚本 O01 系列。

O-02 · 做共存说明和冲突诊断，本轮不做前缀

原方案把覆盖、报错、错参并列为当前宿主后果，实际当前同一层重名明确抛错，带作用域注册才允许遮蔽。前缀只绕过命名，不能解决同文件双写、双注入和用户真源分裂；还要修改工具描述、规则、守卫提示、面板、测试，收益不足以列为首批 P0。

做法：默认保留现有工具名；README 明确同一 profile 不组合两套接管同一记忆的引擎，列出风险；注册失败日志必须标出具体冲突名，不能笼统“工具注册失败”。宿主已有错误即保留原因，不吞掉成成功状态。

明确不做：compat.toolPrefix、多名字别名、为共存拆成第二套写链、未经同装测试的兼容承诺。将来若用户明确需要同装，先隔离 profile/存储职责并实测，再立独立兼容任务；不是现在挂个开关。

验收：模拟同层 memory_read 重名，给出清楚失败且不替换别人的工具；默认工具名保持；文档不声称前缀能实现安全共存。

证据：工具注册、异常处理；Host tools.register Inspect 与当前宿主 dsh-tools/lib/index.js:385。

O-03 · 改后做：先补真实写链，再做准确的批准绑定

先纠正范围与安全承诺

模型没有 replaceDocument／removeSection 独立工具，但能 memory_edit(remove)、memory_replace_section（甚至清空）、memory_restore 和 prune。原动作覆盖漏了这些。面板单条删除也并非每次弹确认。裸 write/edit/apply_patch 已有守卫，但不拦任意 shell，这一层是防误操作，不是执行环境安全边界。

类别最小要求确认策略建议
普通追加共享文件锁、同请求去重、备份与写后通知；expectedRevision 仍可选，因为追加可合并当前内容。不增加固定确认回合。
修改／移除一个明确条目强制 expectedRevision；只匹配一个完整条目；备份、幂等。面板已有明确删除点击，模型仍按任务授权执行。不新增每条弹窗或第二次模型 token 回传；不把 CAS 宣传成用户授权。
整节替换／整节删除／整档替换／恢复强制 CAS、展示具体差异或准确影响、保留回滚点；模型侧整节替换和恢复也算批量操作。进入可预览的批准计划；旧文件划分必须真人确认，批量破坏操作建议复用同一真实批准状态。没有可用批准通道就拒绝批量应用，普通读写仍可用。
归档日期文件计划绑定准确日期集合与每个源文件 revision；归档与写日记共用锁；部分完成可见。预览后真人选定并应用；不能仅凭 dryRun:false 或模型回传 token 认定用户同意。

上表的批量真人批准策略是本次复审建议，不是用户已经批准的新增权限规则。已明确同意的旧文件划分确认不能被普通工具创建核心标题所绕过。

必须先修的实测缺口

  1. CAS 在 store 强制。除 restore 外目前都允许省略。对 edit／editAt／remove／replaceSection／removeSection／replaceDocument 强制版本，校验发生在锁内。面板冲突后不能删除 revision 强盖，应重读、比较、重新批准。
  2. 去重移到同一锁内、CAS 之前。两个相同 operationId 排队实测写入两份。回执绑定规范化目标＋动作／mode＋请求正文指纹，同 ID 不同内容报 operation_mismatch，不误报 duplicate；restore 和 prune 也返回一致重放结果。
  3. 确认回执与可选日志分开。现有 operationLog 可关闭、末 500 条、有吞错，不能当关键批准账本。关键计划在 stateDir 保存有界状态：pending／approved／applying／committed，绑定来源项目、版本、影响与新内容 hash。模型能拿到 planId 不等于能把状态改成 approved；由受信任用户动作批准。计划过期或配置／路径／正文变化重新预览。
  4. 不要许诺跨崩溃绝对一次。写前记录 applying，写后核对新 revision 并保存回执；失败或崩溃恢复时先比对旧／新版本，不自动重做未知副作用。到期回执清理、日志关闭的保证范围要写清；无幂等键不能承诺重试自动去重。
  5. 备份名加唯一后缀并防覆盖。实测同毫秒两次写只留一份，初始版本丢失。名称使用时间＋随机 ID；批量修改要求有效快照，backupKeep:0 下拒绝这类操作并说明需启用备份，不静默违反可恢复承诺。
  6. 归档真正串行化。项目归档锁后按固定顺序取已选日期文件锁，持锁验证集合与 revision，再移动已批准集合；新增文件不顺手归档。发生部分错误返回 partial 及已移动／失败清单，不再 ok:true 模糊带过。原始归档可人工移回，但现 memory_restore 不支持日记，不能宣称已有一键归档恢复。

保持一个 store 写路径；入口只提供来源与展示，不各自重写门禁。现有面板 connection 信任栅栏继续使用。批准 UI 的具体承载需要按最终产品设计确认，不能用这份工程复审擅自批准“用户复制 revision”交互。

不做：额外模型整档写工具、每次追加二次确认、机器判断“已充分蒸馏”、全面封锁 shell、非合作外部编辑的原子 CAS 承诺。外部写恰在检查与 rename 间仍有窗口，备份不保证保存其竞争版本。

验收：所有真实入口参数化测 CAS；同 ID 排队只落一份、跨目标同 ID 拒绝、restore／prune 重放一致；源集合／正文变动不能套旧计划；备份同毫秒不覆盖；持日期写锁时归档等待或拒绝；部分失败明确报告；关闭日志不能关闭关键批准回执。

证据：模型工具、去重和备份、共用写链、归档、冲突覆盖。验证脚本 O03 系列。

O-04 · 做，先修“配置值读错”，再谈删键

schema 实有 37 个叶键，均能找到 Host 或 Client 读取点。没有证据支持本轮按“死开关”删除一批键。现有 conflictPolicy 已删除且有测试，保持即可。

实测高优先级缺陷：Config 的标准解析返回 volatile 引用对象，现 normalizer 只认原始类型。输入 readOnly:true、search.enabled:false、user limit:3000，经 schema 后再归一化变为 false、true、8000，workbuddyHome 也回退空值。不能靠目前直接传原始对象的测试证明运行时配置有效。

具体怎么做

  1. 归一化前正确解包 volatile 引用，对原始对象保留兼容；不能改写引用本身。增加“真实 schema.validate → apply → 工具／注入”的集成测试。
  2. 保持稳定 cfg 对象供现有 closures 使用；监听当前宿主 loader/volatile-update，重读有效值、原地更新归一化配置并使相关快照失效。普通键仍按宿主重载生命周期，不手写 profile 配置文件。
  3. 对于改变注册集合的 ui.enabled、search.enabled、guard.enabled，重建该插件拥有的子作用域并 dispose 旧注册；Client 入口也必须随配置实际增删，不能只更新 flags。目标最低版本无对应事件时应有明确重载策略并实测，不能降级成“保存成功但不生效”。
  4. 明确权限：readOnly 优先拒绝所有插件写；write.enabled 是写能力总闸；ui.allowWriteActions 只控制面板写，不再隐藏只读备份查询；工具批量能力按写权限与批准状态控制。收紧跨界耦合需要迁移说明，不能悄悄放宽已有显式禁止。
  5. 0 预算真正不贡献内容（含画像歧义分支）；保留显式 ensureLayout:false，但新默认为首写创建，所有合法性检查先于 mkdir。
  6. 只修 env.js 单候选分支的 uidFromPersonalDir(dirname(path))；多候选精确 uid 选择已正确，不改成别的匹配规则。

不做：按键数硬砍配置、把 readOnly 与 write.enabled 当同义直接删一个、未知旧键导致启动崩溃、把旧全文预算静默解释成新分层预算。

验收：真实包装值启动与热更新均生效；关闭搜索／UI／守卫后注册数正确且无重复；readOnly=true 时工具与面板均拒写；37 键都有读取点与生效时机；0 预算、uid 单/多候选、无效首写不建目录。

证据：原始值判定、一次归一化、uid 两分支、跨界工具开关；当前 loader/lib/index.js:526–553。验证脚本 O04 系列。

O-05 · 修会话快照，不把所有状态都会话化

全局 recent/catalog 是“所有工作区总览”，有合理用途，不能因为是单例就判串台。项目面板也已经能按 sessionId 解析项目并有测试。真正的缺口是 first-turn 按 cwd 冻结：新会话会拿旧会话的快照；面板写还只清 catalog，没通知注入失效。

做法：每个实际会话对象保存有效 cwd、配置代次、冻结快照和最后装配信息；优先 WeakMap，不为持久会话 ID 永久留无界 Map。拿不到会话标识就退回每次装配缓存，不共享 '(no-session)' 假键。同会话切换 cwd 重新选项目；当前 workingDirectory.get(session) 可用时读它，旧版明确回退 header.cwd，不猜 process.cwd。

写后通知从 store 的成功提交统一发出，带变更路径与结果；工具／面板都接同一路径。首版保留 on-change 语义；现有 first-turn 作为兼容模式改为真正会话范围，仍保留已约定的写后显式刷新，文档不叫它绝对整会话冻结。

不做：会话版项目总览、把锁／备份／幂等账本按会话拆开、silentPresets 黑名单。当前宿主 complete prompt 只保留完整段，“minimal 仍注入本插件四段”不是当前事实；工具 schema 是另一条独立通道，不能混为一谈。

验收：同 cwd 两个新会话各自初次取值；不同 cwd 交替；会话 cwd 改变；工具和面板写后相同策略；无会话不串台；插件卸载清理注册与缓存。

证据：按 cwd 冻结、总览与写通知、总览来源、会话面板已有测试。验证脚本 O05。

O-06 · 做稳定、透明和少读盘；本轮不默认按轮冻结

按步装配的事实成立，全文 cache 工厂也确实尚未接入。实时字符数造成抖动、status 把估计当注入量都是真问题：关闭注入时实测 status 仍说用户 injected=25。但“写一次整段重算”取决于当前提供方能力：in-history 路由可以追加系统更新保留前缀，同时累积版本；不能一刀切算账。

具体怎么做

  1. 分层常驻只含核心、受限标题目录、固定规则；同主题正文新增但核心/标题不变时，本插件的常驻文本逐字不变。
  2. 去掉动态 chars、时间和命中次数；保留稳定的“有未注入内容”等必要状态。不是“规则永远不能出现任何数字”，固定编号和固定预算说明不是实时抖动。
  3. 使用一处有界文件快照缓存：统一安全字节上限、规范路径与 stat 指纹（至少 mtime/ctime/size），容量与总缓存字节有限；读取内容与压力统计复用同一快照。自有写后定向失效，不能无界缓存整文件或失去原 maxBytes 限制。
  4. 记录本插件各块在当前会话最后一次装配的真实码元数、截断、有效模式与来源版本；没有实际装配返回 null。区分“本插件提供的块”与宿主最终接纳的完整 system，complete 覆盖后不可把 provider 文本称为实际模型输入；无法观察最终采用则明确标注口径。
  5. 成本对照记录主模型输入／输出、cacheRead／cacheWrite、工具回显和延迟；不可得写未知，不用字符直接换算费用。包括 in-history 历史累计与整理成本。

本轮不做：新增 turn-start 并设默认、按 cwd 清轮缓存、全文迁 context、自研历史投影。若日后真实工作负载显示核心在同轮频繁变化且收益足够，另做会话／轮级冻结验证；当前先减少无关正文变化，比增加新模式更直接。

验收：内容不变时命中缓存且无全文重读；本插件写后更新、外部 stat 变化可见；长尾正文变化不改常驻；禁用时明确 0／未装配 null；缓存达到容量会驱逐；不宣称零 token 成本。

证据：未接入的文件缓存、动态提示与读取、推断 injected；当前宿主 system-prompt README:154–156、agent-loop README:160–166。

已有版本冲突、顺序幂等、两个并发追加、锁超时、活进程锁、备份失败和恢复测试。原文“都没有”不成立。239 项通过与新复现缺口并不冲突，因为这些边界没被测到。

新增优化 · 9 个模型工具逐项精简

2026-11-16 补充。用户明确提出：memory_prune 不需要给模型，UI 已能手动归档；其余工具都要一并评估。当前仍是 9 个注册工具，本节给出设计建议，没有修改产品。移除其余入口与补 UI 的具体实施尚待确认。

推荐目标：默认 9 个减为 5 个。保留 memory_status、memory_read、memory_search、memory_append、memory_edit；归档、整节整理、备份列表与历史恢复交给用户管理入口。减少的是模型可调用入口，不删除文件存储、备份或 UI 管理能力，也不把功能藏到一个巨大的 memory_manage 工具里。

1. 为什么这样划分

模型日常必须能找回经验、追加新结论、修正过期条目，也需要解释“为什么读不到／写不了”。归档旧文件、整体整理和历史回滚则是低频管理动作；已有 UI 或已确认的整理预览方向可以承接，更适合由用户查看影响后决定。归档由 UI 承接是用户已经提出的要求，其余归属是本次评估建议。

当前工具决定理由及替代实现边界／验收
memory_status保留，缩小默认回显模型排障需要路径来源、有效模式、可写状态、截断原因；无面板时尤其有用。其声明仅约 256 字符，是最小的工具；与 read 合并只为减一个名字，不值得引入全局诊断分支。默认只回与当前会话相关的摘要；详细配置与长目录留 UI 或显式排障扩展，不每次回显全部配置、日期文件。保留只读，不新加“高级工具模式”。
memory_read保留有界全文／章节读取、目录和完整 revision，是渐进式披露与安全编辑的必要入口。延续 O-01 的分页、截断与完整版本修正；不合并搜索、恢复、归档分支；只读画像目标可复用这个工具，不另起画像工具。
memory_search保留主题不明确时搜索项目、用户和日期笔记；已有清楚的 scope 与限制。移除会迫使整文件读取，破坏分层收益。结果有界、来源清楚、命中和文件截断分别说明；关闭搜索沿用现有显式设置，不新增工具数量预设。
memory_append保留低影响的日常记忆写入；也可继续记录日期笔记。与更新的参数及权限不同，保留独立入口更容易用对。首写创建、幂等与写锁按 O-03/O-04 修正；不夹带归档、整档覆盖或自动分类系统。
memory_edit保留 replace／remove 单条模式纠正失效事实、替换一条和明确删除一条是日常维护。把 remove 也收回 UI 会迫使用户为每条错误介入。强制 revision、完整单条、歧义拒绝、备份和重放校验；不偷偷扩成批量操作、不允许多条替换文本伪装为一条。继续防止通过普通编辑暗中迁移旧文件。
memory_prune从模型目录移除用户已可在 UI 预览、选择日期、手动归档。保留两个执行入口没有必要；日期笔记本来就不常驻，归档也不应成为每轮模型任务。删除模型注册与专用工具包装，保留 store.prune、UI dialog、POST action。规则不再让模型按年龄调用归档；UI 仍须修计划绑定、写锁、重试与 partial 报告，不能因移除工具就视为存储问题已修好。
memory_replace_section从模型目录移除；整理经 UI 应用一次替换整节确实比多次 edit 高效，但影响面大。默认分层后，长尾资料大不等于必须反复压缩；用户要求的整节整理可由主模型生成完整草案，经 UI 差异预览后一次提交。保留 store.replaceSection 与面板章节编辑。已有章节编辑并不等于已有版本绑定草案批准，须按整理设计补齐后再视为替代完成。不让模型为绕过已删除的工具拆成大量 edit；显式少量逐条纠错仍可。无批准通道就停在草案，不恢复模型批量入口。
memory_list_revisions与 restore 一起移至 UI备份浏览是低频管理。若恢复只在 UI，模型不再需要枚举备份文件名；只撤 restore 仍留 list 不是完整精简。当前有 GET /revisions 与 /revision，但 Client 没有完整历史浏览器。先补一个文件内“历史版本”入口＋选择列表与差异预览，再与 restore 配对撤注册；不删除备份存储或后端查询。
memory_restore从模型目录移除；用户批准 UI 恢复回退可能覆盖后来新增结论，适合由用户看差异后执行。现有 UI 只有最近写入的短时撤销，不能当作任意历史恢复替代。与版本列表 UI 同批落地：选择备份→读取完整当前版本与历史版本→预览→强制当前 revision＋幂等键→保存前备份当前文件。保留即时撤销与 store.restore；恢复不能跨目标、不能因切换文件继续用上一文件的备份／revision。

2. 两条可行路线与本稿选择

保守路线是 8 个：现在只撤 prune，其余保留。独立审查也建议这一尺度，因为 headless 仍可整节整理和历史回滚，且不用新补 UI。它是合理的短期落地次序，不能为了宣称少四个而提前撤掉没有替代的能力。

本稿建议的产品目标是 5 个：明确把低频管理交给用户 UI，完成下文前置条件后再撤整节替换及版本工具。它需要新增轻量历史入口，也失去无 UI 环境的模型批量整理／回滚便利。选择它的理由是减少长期管理 schema 和模型误用面，同时与“主模型给草案、用户确认整理”一致；不是各审查者已经一致认定“删得越多越好”，也不是用户已同意这三项额外移除。

3. 为什么不强行合成 4 个或 1 个

不合并 status/read：当前 status 的声明只有 256 字符，read 已有 target、section、sectionsOnly、limit 等读取参数。为了少一个名字加入“诊断视图＋可省略 target＋另一种回包”，会增加用法分支，且未必节省同等声明体积。先压缩默认状态回显更直接，避免读取正文时顺带回显整套配置。

不合并 read/search：读取一个已知目标与跨文件匹配有不同参数和限额；目录能指明章节时直接 read，信息不足时 search。合并成 query 模式会引入互斥参数，收益只在名字数量上。

不合并 append/edit：追加允许无旧版本合并，编辑必须持已读版本且定位唯一条目。保留独立 schema 能让模型更清楚授权边界，不需要让一个 memory_write 的 action 字段承载各种可选参数。

不新增模式：不做“基础／高级工具集”开关，不借工具懒加载继续保留全部管理入口，不保留会常驻占位的旧工具别名。内部仍复用探测、校验、lossless 与 store；外部职责清楚不等于复制内部实现。

每次模型工具请求与结果也消耗上下文。整节替换一次完成的任务若硬拆成多次 edit，可能抵消声明节省；因此推荐把批量整理改成“一次草案＋用户确认的一次提交”，并明确禁止为工具精简而自动循环逐条压缩。日常只改一两条时仍正常使用 edit。真实 token 和任务延迟按 O-06 同一路由对照验证，不宣称节省 45.1% 费用。

5. 实施顺序：按能力承接分批，不增加永久兼容开关

  1. 先撤 memory_prune 的模型注册和专用包装，同时改中英规则、工具说明、测试清单；UI 与 store 原样保留职责，安全缺口按 O-03 修。
  2. 补轻量的历史版本选择／差异预览／强制版本恢复，保留现有短时撤销。确认这些真实可用后，在同一批次撤 memory_list_revisions 与 memory_restore，不给用户留下只能撤销 10 秒的恢复退化。
  3. 旧文件／整节整理的草案预览与一次提交可用后，撤 memory_replace_section；原 UI 章节编辑继续可用。补未批准不写、旧基线拒绝、操作重试只提交一次的测试。
  4. 最终默认基础集合固定为五个；search.enabled=false 时可沿用原设置少注册 search，但不新增一个精简等级开关。状态默认只返回简短必要信息。迁移说明列出撤掉的工具与 UI 去向，删除常驻规则中的旧名称；不留返回“请去 UI”的工具空壳。

无面板场景仍能日常读、搜、追加、单条编辑和排障，但不再通过模型归档、整节整理或回滚历史。管理操作需用户使用带面板的 profile，或通过受信任本地编辑方式完成；不提示模型绕用 shell／write 编辑记忆，不因缺 UI 自动重开管理工具。这是通用插件的明确能力边界，不是悄悄丢掉 headless 支持。

6. 对原复审结论的更新

本节是 O-03、O-04、O-07、O-09、O-11 的补充：不再为了给模型保留批量管理而新增通用模型审批工具。O-03 的 CAS、锁、备份、计划集合绑定、幂等与可信批准仍在共享 store 和用户管理入口落实；删工具不会修复 UI 仍在调用的漏洞。O-04 不再用面板开关决定备份工具是否注册，因为这两个模型工具将配对撤去；O-07 把模型包装测试替换为“注册集合确实缩减＋UI端到端仍可用”，store 回归保留；O-09 的主模型草案仍可在会话中给出，应用交给 UI；O-11 必须同步中英写入规则与恢复说明。

本稿前面以当前 9 工具为基础分析的“模型可调用整节替换／恢复／归档”仍是现状证据；在精简落地后应更新为历史基线，不能继续以那些旧入口规划新产品。

7. 验收条件

  • 默认注册集合只含五个基础名字；四个撤掉的管理工具不再出现在 schema、工具说明、常驻规则或旧别名中。旧调用明确失败，不假装执行成功。
  • UI 归档仍能预览、选择、应用；当前 store 的计划漂移、锁与 partial 问题仍有回归；没有为了去工具而删 action 或 store 方法。
  • 任意保留备份能由用户在 UI 选择、预览并恢复；不止当前会话的 10 秒撤销。恢复前备份和目标绑定正确，读不到完整快照时拒绝应用。
  • 模型仍能在默认分层下直接读核心／按需搜资料、追加和精确修改／删除一条；用户要求批量整理时生成草案，不自动拆成多次破坏性编辑。
  • 同目标草案的基线变动、目标切换、重复确认与回放均按 O-03 拒绝或幂等处理；headless 报出管理入口不可用，不引导绕守卫写入。
  • 重新测实际工具声明和同批任务的 token／往返，单独报告 UI 管理的交互成本；不能以工具少四个替代总成本验收。
