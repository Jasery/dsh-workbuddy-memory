从 app.asar 逆向还原的完整读写链路：存储格式、注入管线、路由门控、写入约束、并发防护。

逆向对象 WorkBuddy 5.9.3 app.asar 181,996,084 B / 9893 files 宿主 main/authority-snapshot.js 本机路由 LEGACY 2026-11-06

一句话结论：WorkBuddy 的记忆系统是「文件即权威存储 + 提示词即写入逻辑」——宿主只负责读文件、做脱敏和截断、拼进 system prompt；真正决定写什么、写到哪个文件的不是代码，而是注入的那几段提示词，写入动作由模型用通用 Edit/Write 工具完成。

这意味着：要兼容它，重点不是复刻 API，而是复刻注入文本 + 文件布局 + 版本栅栏这三件事。

  1. 注入是「首轮一次」而非每轮。所有记忆 Section 的 stage 都是 first_turn，且被 alreadyInjectedUserContext 与 hasPriorUserMessages 双重拦截。进入对话历史后靠 prompt cache 存活，后续轮次不再重新读盘。
  2. 工作区长期记忆自动注入，每日流水不注入。<cwd>/.workbuddy/memory/MEMORY.md 会整篇进 system prompt；YYYY-MM-DD.md 只在提示词里给出路径和使用规则，由模型自己 Read。
  3. 两套完全不同的实现并存。LEGACY（本地蒸馏档案 + 三层提示词）与 PLATFORM（云端 MemoryRecall/MemoryUpdate 工具 + <memory_index>）。由服务端下发的路由快照决定，一旦会话创建即冻结。
  4. 用户画像有路径脱敏。Windows 盘符、~/、Unix 常见根目录开头的绝对路径在注入前被替换成 [path omitted]，模型永远看不到真实路径。
  5. 蒸馏档案有严格的版本栅栏。写入前比对 Version：小于现有值直接判 stale 丢弃，等于则视为幂等成功，只有更大才落盘——且全程持文件锁、先备份后原子替换。
  6. 项目记忆没有版本栅栏，纯靠提示词约束。这是整套设计最脆弱的地方：模型被要求「完成后立即追加」，但没有代码强制。零点的 git 同步任务与 WorkBuddy 自身的 LLM 重写会与外部写入者发生真实竞争。

二、存储布局

2.1 目录与文件

宿主用两个可被环境变量覆盖的根：WORKBUDDY_DATA_FOLDER_NAME（默认 .workbuddy）与 WORKBUDDY_CONFIG_DIR（默认 ~/.workbuddy）。工作区记忆固定在 <cwd>/<dataFolderName>/memory。

2.2 蒸馏档案格式

全局画像文件不是普通 Markdown，而是双写结构：给人看的 Markdown 段落 + 给机器看的 JSON 块。解析器优先读 JSON，失败才退化到正则。

# User Memory Profile
> Last updated: 2026-09-29T14:30:23+08:00
> Version: 84

## Memory Block

**工作背景**
…自然语言段落…

**近期动态**
- …

---

<!-- RAW_JSON_START
{
  "uid": "b157244a-…",
  "memoryBlock": "**工作背景**\n…",
  "version": 84,
  "updatedAt": "2026-09-29T14:30:23+08:00"
}
RAW_JSON_END -->

对应的解析与序列化是一对纯函数，位于 main/authority-snapshot.js：

function parseMarkdown(text, uid) {
  // 1. 优先 RAW_JSON：正则匹配 JSON 块，uid 不一致时强制覆写为传入 uid
  const raw = text.match(/<!-- RAW_JSON_START\n([\s\S]*?)\nRAW_JSON_END -->/)
  if (raw) try {
    const obj = JSON.parse(raw[1])
    return obj.uid === uid ? obj : { ...obj, uid }
  } catch {}

  // 2. 退化：Markdown 三件套，任一项缺失都不报错
  const version = text.match(/^>\s*Version:\s*(\d+)/m)
  const updated = text.match(/^>\s*Last updated:\s*(.+)$/m)
  return {
    uid,
    memoryBlock: text.match(/## Memory Block\n\n([\s\S]*?)\n\n---/)?.[1]?.trim() ?? '',
    version: version ? parseInt(version[1], 10) : undefined,
    updatedAt: updated?.[1]?.trim(),
  }
}

toMarkdown 是它的逆运算，字段顺序与分隔符完全固定（## Memory Block 后必须空行、正文与 JSON 之间必须 ---）。这意味着任何外部写入者只要改动这些分隔符，就会让解析器掉进退化分支。

三、注入管线

3.1 Section 体系

WorkBuddy 的自研宿主没有 DSH 那样的 prompt assembly waterfall，而是一套 Section 数组 + stage 标记的简单机制。每个 Section 声明三个属性：

属性取值含义
stagefirst_turn / every_turn只在会话首轮渲染，还是每轮都渲染
roleuser-context / additional-data拼进 system prompt 还是作为独立 user 消息
shouldApply(ctx)布尔二次门控，通常检查模式与注入标记

与记忆相关的四个 Section 全部是 first_turn：

Section产出门控条件
IdentityContextSectionSOUL / IDENTITY / USER + 产品身份 + 语气 + 自定义指令alreadyInjectedUserContext !== true 且非 quick
ProjectContextSection<project_context>：CODEBUDDY.md / AGENTS.md + 目录树同上，且 cwd 非空
ProjectRulesSection<project_rules>：.codebuddy/rules/同上
MemoryIndexSection<memory_index>：云端记忆索引仅 PLATFORM 路由 + 首轮 + 非 ask

3.2 四个注入块

记忆内容本身由 WorkbuddySystemPromptService.renderSystemPrompt() 通过 Nunjucks 模板渲染，四个变量按固定顺序落在 workbuddy-prompt.tpl 第 20–23 行——紧跟在「dataFolderName 不是临时缓存」之后、<content_policy> 之前：

{{ WorkbuddyMemory_1 }}      → 记忆系统的使用说明书（约 3.5 KB）
{{ WorkingMemoryContent }}   → <working_memory_content> 项目 MEMORY.md
{{ UserInstructionsContent }}→ <user_memory> / <user_instructions> 用户 MEMORY.md
{{ UserMemoryContent }}      → <memory> 服务端画像（已脱敏）

块 1：使用说明书

不是数据而是规则。LEGACY 下由 getWorkbuddyMemory1() 内联生成，内容与磁盘上的 prompt-common/fragments/workbuddy-memory-system.md 同源但多了两段项目隔离警告。核心约束：

层写入工具限额触发条件
云画像 <memory>禁止本地修改—服务端托管，下次会话覆盖
用户级 ~/.workbuddy/MEMORY.mdEdit 就地改4,000 字符/会话用户明确要求长期记住、且不属于某项目
项目 MEMORY.mdEdit 就地改3,000 字符/会话用户分享了项目约定或偏好
项目 YYYY-MM-DD.mdEdit 追加无完成实质工作后立刻记，append-only

「实质工作」被明确定义为 6 类：建改网站/应用、修 bug、写报告/文档、重构或架构变更、选定技术方案、用户分享项目约定。明确禁止记录：搜索结果、临时路径、工具错误、命令清单、原始工具输出。

还带一条 30 天维护指令：把超过 30 天的日期文件按主题蒸馏进 MEMORY.md，然后删除旧文件。这条是模型自己执行的，没有后台任务。

块 2 / 3：项目与用户记忆

getWorkingMemoryContent(memoryDir, platform) {
  读 <memoryDir>/MEMORY.md
  空 → 返回 ''
  ≤ 10000 → <working_memory_content>
               The following is the existing working memory for this project. Use it as context.
               {原文}
             </working_memory_content>
  > 10000 → 截到 10000 + "... (memory truncated — MEMORY.md is too large)"
             + 平台/遗留两种后续指令（PLATFORM 让去读全文，LEGACY 要求立刻整理）
}

getUserInstructionsContent(userDir, platform) {
  读 ~/.workbuddy/MEMORY.md
  限额 4000，超出截断
  PLATFORM → <user_instructions>  "user-provided preferences, standing instructions…"
  LEGACY   → <user_memory>        "your long-term user-level memory, persisted across all projects"
}

两种模式的包装标签不同不是装饰：LEGACY 的 <user_memory> 语义是「记忆数据」，PLATFORM 的 <user_instructions> 语义是「用户指令，需优先遵守」。同一份文件，注入语义完全不同。

块 4：服务端画像

collect() {
  if (!isCloudMemoryCollectEnabled)  → skip cloud_memory_disabled
  if (!uid)                          → skip user_not_logged_in
  if (!gateSnapshot && DisableMemoryPersonalization) → skip feature_disabled

  route = PLATFORM ? 'platform' : 'legacy'
  block = route === 'platform'
        ? resolvePlatformMemoryBlock(uid, enterpriseId, locale)
        : resolveMemoryBlock(uid, locale, isSameAccount)

  if (!isSameAccount())              → skip account_changed
  if (gateRevision 变化)             → skip cloud_memory_disabled   // 并发改写检测
  if (skipReason)                    → skip skipReason
  if (!block)                        → skip empty_memory_block

  text = truncate(sanitize(block), limit)

取值路径：LEGACY 先读本地档案，本地没有再打 GET /api/memory/profile 取 data.foryou_prompt；PLATFORM 走 resolvePlatformMemoryContext，读本地归档未命中则拉远端并异步回写归档。两种模式都有短 TTL 缓存（1s / 30s）与失败冷却（30s），避免每次 turn 都打网络。

3.4 路径脱敏

注入前，服务端画像会过一遍 sanitizeMemoryBlock，把三类绝对路径整段替换成 [path omitted]，并统计替换次数写进日志：

正则覆盖
[A-Za-z]:[\\/]…Windows 盘符路径
~/…POSIX 家目录简写
/(Users|home|Volumes|private|tmp|var|mnt|media|opt|srv|root|data|Applications|Library)/…Unix 常见根，带负向前瞻避免误伤 URL 与代码

这条机制解释了为什么注入的画像里会出现「本地仓库 [path omitted]」这类断句——是宿主抹掉的，不是模型写的。项目级 MEMORY.md 不过这道工序，路径原样注入。

四、双路由与门控

4.1 LEGACY 与 PLATFORM

两套实现不是版本过渡，而是并行存在的两种产品形态，由服务端下发的 gate snapshot 决定：

维度LEGACYPLATFORM
画像来源本地 _memory.md → 远端 /api/memory/profile本地归档 → 远端 memory context
画像限额10,0002,000
记忆索引无<memory_index>，≤1000
读取工具无专用工具MemoryRecall
写入工具无专用工具，用 EditMemoryUpdate
用户记忆标签<user_memory><user_instructions>
项目提示词三层完整版（含"何时写"清单）精简版（getWorkspaceMemory1，写入让位给记忆工具）

路由状态机有四个值：LEGACY / MIGRATING / PLATFORM / FAILED。会话创建时冻结一次（freezeMemoryRouteForConversation），中途服务端改配置也不会切换——避免同一会话里记忆语义漂移。

function computeCloudMemoryPlatformEnabled(route) {
  return isMemoryPlatformV2Allowed()        // 灰度开关
      && isEffectiveCloudMemoryEnabled()      // 用户设置 && 企业策略
      && route === 'PLATFORM'
}

// 非 PLATFORM 时这两个工具被列入禁用名单
const platformOnlyTools = ['MemoryRecall', 'MemoryUpdate']

五、写入路径

这是整套设计里最"轻"的一环，也是唯一没有代码强制的一环：

没有任何专用写入 API。提示词直接告诉模型：用 Edit 工具改文件。宿主端不存在 memory write 接口、不存在 schema 校验、不存在内容审核（除了"不要存密钥"这句口头约束）。

实际约束全部来自文本：

约束文本表述强度
写入时机完成实质工作后、给出最终答复前强（MUST follow）
写入目标默认当日 YYYY-MM-DD.md；项目约定才进 MEMORY.md强
追加语义日期文件 append-only，永不覆盖强
额度项目 MEMORY.md 3000 字符/会话、用户 4000中（无运行时校验）
内容边界不记搜索结果、临时路径、工具错误、命令清单中
密钥永不落盘，即使明确要求强
蒸馏>30 天的日期文件按主题合并进 MEMORY.md 后删除弱（靠模型自觉）

这种设计的代价很明确：写入质量完全取决于模型是否遵守提示词。没有幂等键、没有去重、没有冲突检测——同一个事实可能被反复追加到多天的日志里，也可能因为模型"觉得不值得记"而丢失。

唯一有代码保障的是日期文件的命名：提示词里的 {{ WorkbuddyMemoryDir }}/YYYY-MM-DD.md 会被替换成真实绝对路径，模型照着写；目录不存在时提示词明确要求先创建。

六、档案读写机制

与服务端画像相关的读写是全系统唯一有完整并发防护的部分，值得逐层拆开。

6.1 写入：锁 → 版本栅栏 → 备份 → 原子替换

doWriteWithLockAndGuard(uid, profile, dirs) {
  ensureDir(primaryDir)

  // ① 独占锁：.<uid>.lock，ttl 10s，最多重试 3 次，间隔 150ms
  lock = acquireFileLock(`.${uid}.lock`, { ttlMs: 10000, maxRetries: 3, retryDelayMs: 150 })
  if (!lock) return { success: false, errorCode: 'lock_contention' }

  // ② 版本栅栏 —— 三道分支
  existing = tryReadExistingVersion(archivePath)
  if (typeof profile.version === 'number' && typeof existing === 'number') {
    if (profile.version <  existing) return { success: false, errorCode: 'stale_version', skipped: true }
    if (profile.version === existing) return { success: true,  skipped: true, skipReason: 'same_version' }
  }

  // ③ 备份现有文件 → <uid>_memory.md.bak（copy 到 temp 再 rename）
  if (await fileExists(archivePath)) { copyFile → tmp; rename(tmp, backupPath) }

  // ④ 原子写：写 temp 再 rename，绝不产生半截文件
  writeFile(tmpOf(archivePath), toMarkdown(profile))
  rename(tmp, archivePath)
}

三道版本分支的语义值得注意：

  • 小于现有 → stale_version，丢弃且报告失败。防止慢速网络回来的旧快照覆盖新数据。
  • 等于现有 → same_version，报告成功但跳过写入。天然幂等，重复拉取不会反复写盘。
  • 大于现有 → 正常落盘。

6.2 读取：三级回退 + 自动迁移

doRead(uid, dirs) {
  // ① 新目录
  try { return parseMarkdown(await readFile(join(primaryDir, `${uid}_memory.md`)), uid) }
  catch (ENOENT) {}

  // ② 历史遗留目录（拼写错误：memery）
  try {
    const legacy = parseMarkdown(await readFile(join(legacyDir, `${uid}_memory.md`)), uid)
    if (legacy) {
      queueMicrotask(() => writeProfile(uid, legacy, dirs))   // 后台迁移，不阻塞本次读取
      log.migrated({ source: 'legacy_memery' })
      return legacy
    }
  } catch (ENOENT) {}

  // ③ 都没有
  return null
}

整个读/写/删都套了 timeoutMs = 1500 的超时和 trace 日志（trace_id / uid / cost_ms / op / error_code），失败分类为 timeout / parse_error / io_error / unknown。

6.3 谁在写这个文件

关键点：LEGACY 模式下客户端不写本地档案。resolveMemoryBlockUncached 只读不写；唯一的写入路径 persistArchive 只在 PLATFORM 分支被调用（远端拉取成功后归档）。

所以本地 _memory.md 的 Version: 84 这类递增，来源是另一个通道（账号级云端同步），对逆向记忆管线本身不构成影响——但意味着外部工具不应写这个文件：版本比对会让它被判 stale 或被下一次同步覆盖。

八、逆向附录

8.1 asar 结构与提取方法

Electron asar 是「8 字节头 + 4 字节长度 + JSON 目录 + 拼接的文件数据」。头部布局：

offset 0   uint32 = 4
offset 4   uint32 = headerSize
offset 8   uint32 = jsonSize      // 实测 2,609,603
offset 12  uint32 = 校验/对齐
offset 16  JSON 目录（9893 个条目，flatten 后每个带 size / offset / unpacked）
BASE = 16 + jsonSize              // 实测 2,609,619，文件数据起点

注意两个细节：offset 是字符串而不是数字（超过 2^31 的大文件），必须 Number() 转换；标了 unpacked: true 的文件不在 asar 里，要去 app.asar.unpacked/ 同名路径下直接读——提示词片段和模板全部是 unpacked，省了不少事。

8.3 检索技巧

压缩产物里所有标识符都被重命名（In、Fn、Ln），直接搜函数名效率低。有效做法是搜字符串字面量——中文文案、日志前缀、错误码几乎不可压缩：

alreadyInjectedUserContext     // 定位 Section 门控
RAW_JSON_START                 // 定位档案格式
not-first-turn                 // 定位判定链
memory_injection_skip          // 定位注入日志
[path omitted]                 // 定位脱敏常量

常量表则通过「赋值语句 + 已知语义值」定位，例如搜 Ln=` 拿到截断文案，同一行里 Fn=1e4, In=2e3 就是两个限额。

九、对独立插件的启示

如果把这份实现当作参照系，做一个兼容 WorkBuddy 记忆的独立插件，需要分三类对待：

类别项目建议
必须复刻 文件布局与目录名<cwd>/.workbuddy/memory + ~/.workbuddy，支持两个环境变量覆盖
四个注入块的语义与边界项目 MEMORY.md 全文、用户 MEMORY.md、画像、规则说明；顺序固定
限额与截断文案10000 / 4000 / 2000，超限要带行动指令而非静默截断
路径脱敏否则会把用户真实目录写进提示词，跨项目泄漏
值得借鉴 版本栅栏的三分支语义stale 丢弃 / same 幂等成功 / 更新才写，比"最后写入胜"稳得多
首轮注入而非每轮省 token 且稳定 prompt cache；变化内容靠工具按需读
日志带 trace_id 与 cost_ms记忆是静默 subsystem，没有日志等于不可调试
必须超越 项目记忆的写入用工具 + 服务端校验替代"提示词自觉"：幂等键、小节级定位、revision 栅栏
并发安全跨进程文件锁 + 提交前 hash 复检，别只防进程内
检索能力原设计只有整篇注入，没有 search / browse，189 个日期文件完全靠模型逐个 Read

最核心的一条判断：WorkBuddy 的记忆系统本质上是一个「精心写好的提示词 + 几个 Markdown 文件」，工程复杂度集中在注入侧（脱敏、截断、门控、缓存、路由）而不是存储侧。要兼容它，读懂那 3.9 KB 的提示词比读 795 KB 的 bundle 更重要——代码只决定了"给不给看"，提示词决定了"记不记、记哪"。
