1. 一句话结论

是同类，但不是同一件事：本项目做的是「跨客户端共用同一份 WorkBuddy 记忆文件」，dsh-memory-palace 做的是「在 DSH 里重建一套会自动写、会自动注入的记忆系统，桥接 WorkBuddy 只是可选兼容层」。

两者都围绕 MEMORY.md + YYYY-MM-DD.md 这套文件式记忆，都给 DSH 注册系统提示词与 memory_* 工具，都会读写 <cwd>/.workbuddy/memory/。但数据主权、写入驱动、注入通道三条主线完全不同：本项目把「文件由 WorkBuddy 拥有」当硬约束；对比项目把「DSH 自己拥有记忆系统」当硬约束，WorkBuddy 目录只被当作一个写入目标。

重叠度
高（用户视角）
同一个插件市场类目、同一套文件布局、同类工具名；普通用户第一眼会认为是竞品。9 个工具里 memory_read 直接同名。
定位重复度
低（架构层）
桥接 / 互操作 vs 移植 / 自建。用户级记忆路径、注入通道、写入触发机制、UI 形态均不同。
成熟度差距
明显
对比项目 3 个月、26 star、33 个 npm 版本、约 6610 次月下载、已收录插件目录、有 CI 自动发布；本项目 2 天、6 个版本、约 473 次月下载、收录 PR 审核中、无 CI。
最需要注意的一条：同装会出问题

两个插件都注册名为 memory_read 的工具，但语义不同（本项目按 target 返回 revision + 小节；对比项目按 scope 读长期记忆/近三天日志）。同时装在同一 profile 里会出现工具注册冲突、同一份 MEMORY.md 被两条互不感知的写链改、以及同一文件内容被注入两遍（系统提示词头截 + 历史投影尾截）。详见第 7 节。该结论为静态分析推论，未做运行时同装实测。

6. 关键差异深挖

6.1 数据主权：一个真源 vs 三层目录 paths.js:93-109 / paths.mjs:15-81

本项目 memoryLayout() 只解析 WorkBuddy 的 home 与项目 memory/；用户级 MEMORY.md、USER.md 与项目级 MEMORY.md、日期文件都在 WorkBuddy 名下。插件自己的 stateDir（默认 ~/.dsh/workbuddy-memory）只放锁、备份、台账，注释明确「derived state, never memory content」。

对比项目则把 .deepseek-harness 永远放在读取列表首位（不加 existsSync 门槛），写入时若存在 buddy 目录就全部同步写入 .workbuddy/memory 与 .codebuddy/memory，都不存在才创建 dsh 目录；用户级完全独立在 ~/.deepseek-harness/MEMORY.md。结果是：同一条事实可能同时落在 3 个项目目录里，而用户在 WorkBuddy 里写的全局偏好，DSH 侧看不到。

实操含义

若目标是「WorkBuddy 里改一条，DSH 立刻看到；DSH 里改一条，WorkBuddy 立刻看到」，只有本项目成立。对比项目在项目级能部分成立（写进 buddy 目录），但用户级必然分裂成两份。

6.2 注入：系统提示词四段 vs 对话历史投影 inject.js:78-96 / projection.mjs:162-197

本项目用 ctx.systemPrompt.section() 注册 4 个固定顺序的段，每段返回空串即被宿主丢弃；缓存分「每次装配」与「首轮冻结」两种模式，写后主动失效。优点是实现稳、总量可预期（最多 22000 字符）、不依赖宿主内部会话结构；缺点是截断从头取，最新写进去的结论反而在超限时最先丢失。

对比项目为了绕开宿主「systemPrompt.section 仅首次注入」的限制，改在 agent/pre-step 里把每个文件投影成一条独立 user 消息，插入 decision.messages；去重判据是首行 heading（编码路径 + 日期）而非内容哈希，compaction 把消息移出 surface 后自动重注磁盘最新版。作者为此照抄了宿主 agent-instructions 的公开三件套，并在 DEVELOPMENT.md §7.4 明确写下契约风险：agent/pre-step 抛错会毁掉整轮 turn，且依赖 sessionProjections / Session.surface / MessageSourceMap.form 这些预览期 API。

对比项目自承的量化副作用

CONFIG.md:64 原文：注入份数 = 用户级 1 + 项目级 MEMORY.md（最多 4）+ 今日日志（最多 3），「实测最坏 8 条消息 ≈ 5 万字符 = 本值的 7.1 倍」；且 workspaceBudgetChars 一身三职（投影上限、日志上限、重整门禁阈值），调大即同时放宽注入量。本项目把预算按块独立配置，没有这种耦合。

6.3 写入驱动：规则提示 vs 每轮子代理 locale/zh.json / hybrid/subagent.mjs:249-445

本项目注入的 6 条规则里，第 2 条直接规定「什么时候该写」（环境非直觉事实、凭据位置与失效、会重犯的坑、用户确认的偏好；一次性问答、中间状态、能从 git log 读出的事实不写），并规定写前 memory_read 拿 revision、遇 conflict 不重试覆盖。落盘完全由模型决定，零额外 LLM 调用。

对比项目把写日志变成流水线：turn/end 缓冲（每会话分桶，30 条 / 30000 字符上限）→ 1.5s debounce → 四道闸门（计划模式 / enabled / 静默 / 有写入目录）→ 子代理用 ctx.llm.stream 跑最多 6 轮工具循环，白名单只有 log_read_section 与 log_write_ops，产出章节化条目并标删过时条目。失败不降级为轻量写入，只留台账。代价是每轮一次模型调用与潜在失败模式；收益是模型「忘了写」也不会漏日志。

6.4 安全与一致性：两种完全不同的防线 write/store.js:585-653 / api.mjs:49-63

  • 本项目防的是「绕过写链」：write/edit/str_replace_editor/apply_patch 一律被 ctx.tools.guard 拦（按 realpath 判定，含符号链接与 Windows 大小写折叠）；面板写路由接宿主 connection.requestRejection，因为写入的 MEMORY.md 下次会被注入系统提示词，等于持久化提示词注入。此外还有 readOnly、幂等键、lossless() 兜底。
  • 对比项目防的是「模型乱删乱改」：删除两阶段 + 宿主原生确认弹窗、整章节 normBlock stale 校验、重整双门禁 + 确认弹窗、计划模式禁写、静默预设工具掩码、API 同源/trustedHosts 校验、子代理 prompt 的「隐私红线」与日志脱敏。
  • 本项目在 README/源码里把并发边界写得很诚实：对不遵守同一把锁的外部编辑器只能「检出已知冲突」，毫秒级并写仍可能被覆盖，靠备份恢复。对比项目 MEMORY.md 写入没有全局锁，只在日志路径上有 promise 链锁。

6.5 UI 形态：编辑器 vs 设置页 src/client.js / client/30-settings-section.js

本项目把「人能直接看懂并改记忆」做成了产品功能：全局总览聚合 DSH 工作区与最近会话目录、项目页签边聊边看、条目 / 小节 / 整文件三级编辑、撤销、归档、冲突重载，全部走同一个 store。对比项目在 v1.8.1 主动删掉了 session header 记忆按钮与手动蒸馏按钮，目前客户端只剩设置页卡片、/记忆重整 命令别名与 nav 星标；记忆正文的修改交给模型工具，没有面向人的浏览器。

9. 决策建议

9.1 按使用场景选

场景建议理由
主力是 WorkBuddy，DSH 只是补充；已有大量 MEMORY.md/USER.md 资产本项目唯一能做到两端同一份文件、同一份用户画像的方案；写入可回滚、有面板可人工修
只用 DSH，希望「装上就自动记」，不介意每轮一次小模型调用对比项目自动日志子代理 + 自动投影 + /记忆重整 闭环，成熟度与分发渠道也更好
重视提示词预算与前缀缓存稳定看具体口径本项目总量上限清晰但每轮重算；对比项目前缀恒定但最坏注入 8 条 ≈ 5 万字符，需手动收紧目录数量
需要人工审核删除 / 回滚本项目（回滚）+ 对比项目（删除确认）两者恰好互补，也是第 8 节 P1 的来源
在同一台机器上两个都想试分 profile 装避免工具同名与双写；用不同 --profile 隔离，不要同 profile 同装

9.2 对本项目的具体动作

  1. 先做定位说明：在 README 增一小节「与 dsh-memory-palace 的区别」，用三行讲清「共用文件 vs 自建系统」「显式工具 vs 自动子代理」「system prompt vs 历史投影」。避免用户在插件目录里二选一时靠猜。
  2. 修真实缺陷：把头部截断改成「保留结构行 + 尾部优先」——这不是抄功能，是修本项目「写了等于没写」的既有问题（P0）。
  3. 处理工具名冲突：至少在文档里写明不兼容；若计划长期共存，提供前缀配置项。
  4. 补工程基建：CI（tag → 测试 → 发布）、收录 PR #14592 跟进（按既有经验，仓库年龄门槛由 regate.yml 自动重跑，不要推空提交催绿）。
  5. 选择性吸收：删除确认、静默预设、双门禁重整可按 P1/P2 排期；投影通道与自动子代理先做技术验证再决定是否引入。
一句话战略判断

不需要把本项目改成对比项目的样子。两者最有价值的差异恰恰是「不自动、不复制、可回滚」——把它守成明确的产品定位，再把对方已经踩过坑并验证过的截断、确认、门禁、CI 机制搬过来，比追逐功能数量更划算。
