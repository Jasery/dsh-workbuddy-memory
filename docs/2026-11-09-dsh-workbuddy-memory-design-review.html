dsh-workbuddy-memory 设计评审

评审结论：REQUEST_CHANGES · 2026-11-09

主审材料：插件设计方案；参考同目录 WorkBuddy 记忆系统逆向报告及本机 DSH 服务契约。

总评

方案目标清晰，围绕共享 Markdown、会话注入、受控写入和本地检索形成闭环；但当前的“锁 + 二次哈希 + 原子替换”不能对不遵守该锁的 WorkBuddy 写者提供无覆盖保证。此外，写入/幂等状态机、批量整理恢复、面板路由授权和会话级工作区选择等协议尚未闭合。建议先修订数据正确性和安全边界，再进入 M2 写入实现。

1P0 · 数据完整性阻断
13P1 · 应先修订/核实
4P2 · 明确边界或跟进

范围说明：这是对设计文本的评审，不是对插件源码的 review。工作区目前只有方案和逆向报告，没有插件实现；因此未声称测试已复现任何实现行为。P1 标记表示设计按当前契约落地时会产生高风险，或发布/权限契约尚未满足。

阻断项

P0跨客户端写入仍存在不可消除的 TOCTOU 窗口 方案 687–704、719–723 行

文档明确指出 WorkBuddy Edit 不认插件的 .lock。DSH 锁内复检哈希通过后，到 temp 文件 rename 替换目标之前，WorkBuddy 仍可写入；随后 DSH 会用基于旧版计算的结果覆盖该写入。复检并没有锁住外部写者，备份若早于外部写入也救不回被覆盖的内容。因而 conflictPolicy: fail 当前并不能保证“冲突不覆盖”。

建议：明确选择一种可兑现的保证：让 WorkBuddy 写入也遵守共同的锁/版本协议；或限制为单写者；或只使用可证明不覆盖的追加/冲突队列。若维持不受控的 WorkBuddy 写入，撤回“默认 fail 可防丢数据”的承诺。写后检测只能发现部分覆盖，不能替代写前的原子条件提交。

高优先级问题

P1revision 与幂等重放状态机定义矛盾 方案 726–747 行

第 737 行把 expected === current 定义成幂等重放并跳过；但首次正常写入时，调用方刚读到的 expected revision 也必然等于当前版本。文档没有规定如何先以 operation key 区分首次请求和重放，因此可能跳过合法首次写入，也可能放行重试并产生重复，需由契约明确，不能靠实现者猜测。

建议：把内容 revision 仅用于乐观并发校验，把稳定 operationId 用于重放识别，并定义“未见该 ID / 已提交 / 进行中 / 失败”的返回语义。revision 相等本身不等于重放。

P1三秒“自写放行”可能掩盖其后的外部版本 方案 745–747 行

文档只说按 scope 记录最近三秒内本插件提交的 revision，命中即放行，未说明是否绑定具体文件、具体操作及当前磁盘哈希。若 DSH 写出 B 后，WorkBuddy 在该时间窗写成 C，下一次 DSH 请求若仅凭旧的“自写”标记绕过复检，就可能覆盖 C。

建议：删除时间窗式栅栏旁路。每次写入都在有效同步机制下核对同一文件当前版本；若要支持连续写，使用 per-file 的成功 revision/链式操作 ID，并仍校验磁盘状态。

P1幂等键缺少目标文件与日期身份 方案 726–730、779–784 行

公式只使用 target、section 和规范化文本，没有规范化文件路径、每日文件日期或操作类型。同一条文本写进不同项目/小节，或在不同日期的 daily 文件追加，可能复用同一键，被错误当作重复。表是否按工作区隔离也未定义。

建议：以 canonical file identity + date + target operation 构造资源作用域，并采用调用方在重试间保持不变的独立 operation ID。定义幂等记录的隔离范围、有效期与冲突行为。

P1幂等账本不与正文文件提交原子化 方案 698–708、726–730 行

写链在目标文件原子替换后才刷新快照/base/幂等表。进程可能在正文已提交、幂等记录未落盘时崩溃；重试若没有稳定 operation ID 的持久化提交记录，可能再次写入。JSONL 的并发追加、裁剪、部分行和启动恢复也未定义。

建议：用持久 journal/原子账本保存 operation ID 与提交状态，并定义崩溃恢复过程，使“正文已提交但未记账”的请求可识别。明确 flush/fsync 的必要范围，写失败时返回可诊断且可安全重试的状态。

P1整理跨文件不是事务，盲目回滚可能抹掉并发写入 方案 789、951–952 行

memory_consolidate 逐条写入目标，全部成功后再删除源；任一步失败则以备份回滚。若进程在部分提交后崩溃，重启无法判断已处理到哪一步；若恢复时其他写者已改过目标，直接还原旧备份会覆盖新内容。部分源删除与回滚再次中断也可能造成重复或遗漏。

建议：为每次整理写 durable journal 和稳定 operation ID；源/目标操作都带 revision 条件，支持幂等重放。回滚只可在目标 revision 仍是本事务产物时执行，否则保留现状并报告冲突，禁止盲目恢复旧快照。

P1重复标题下的小节三方合并身份不明确 方案 755–771、1264 行

算法以 ## 标题 分块并逐节比较，但测试清单同时包含重复小节名。标题相同的两个节点无法仅靠标题唯一配对；插入、删除或重排也会影响序号匹配。若实现采用标题 map 或简单顺序 zip，可能把修改配错节或漏掉节点。文档用 SHA-1 前 8 位作比较值，也不适合作为唯一结构身份。

建议：定义节点匹配和结构变更规则；出现重复标题或无法唯一匹配时 fail-closed，不自动合并。保留全部节点，测试重复标题、插入/删除/重排与多行内容；摘要用完整强散列或直接比较内容。

P1UI HTTP 路由未定义认证和请求来源校验 方案 1010–1036 行

面板通过 GET /content 读取原文、POST /action 修改文件。设计没有说明如何认证 Peer、校验 Host/Origin 或防止跨站请求伪造。本机当前 webServer 契约提供路由注册，但自定义路由需要接入 Connection 的 admission/rejection 边界；不能假设注册路由即自动获得授权。

建议：明确认证模型，优先使用与宿主已认证 Peer 绑定的通道；按需要验证来源并防 CSRF。对未认证 GET 与 POST 都做拒绝测试，并检查部署允许非 loopback 访问时的行为。

P1项目记忆未按会话工作目录选择 方案 314、441–446、544–549、629–642 行

环境探测和目录选择主要发生在插件 apply 阶段；process.cwd() 是进程级目录而非每个会话的有效工作目录。当前 systemPrompt AssembleContext 提供 scope/signal，但并不存在文档所假设的 assembly.variables.cwd。当一个 Host 同时服务多个工作区，会话可能读到或写入别的项目记忆。

建议：从宿主 working-directory 服务按 Agent/Session 取得有效目录；快照、索引、锁与目标路径均按该目录隔离。测试同一 Host 上两个不同 cwd 的会话，确保注入、搜索和写入不串区。

P1画像的 WorkBuddy UID/账户绑定未定义 方案 581–582、1074–1090 行

路径使用 <uid>_memory.md，但设计未说明如何取得当前 WorkBuddy 用户 UID、账号切换后如何失效，或 UID 不可得时是否必须停止读取。多账号场景可能把上一个账号的画像带入当前会话。

建议：把活动身份解析定义为可信依赖；无法确认 UID 时不注入用户画像。账号变化时清掉快照并重新解析来源，状态与诊断中避免泄漏身份或路径。

P1路径守卫既不覆盖旁路工具，也未定义 canonical path 检查 方案 552–570 行

守卫只识别少数工具名以及 file_path/path 字段；shell 或其他文件工具可能不使用该形态。env.isMemoryPath() 的规范化契约未说明：大小写、UNC、8.3 路径、符号链接和 Windows junction 都可能让字符串路径与实际目标不一致。不能把此守卫作为强制授权边界。

建议：按 canonicalized root/target 校验真实路径；明确 symlink/junction 策略，必要时拒绝链接目标。对 shell、别名路径及所有配置的文件写工具做测试。把 guard 定位为防误操作；真正授权需由受控工具集或宿主文件系统策略保证。

P1记忆内容的指令信任边界缺失 方案 580–602、1311 行

项目、用户和画像 Markdown 原文直接进入模型的 system prompt；文件也可能被 WorkBuddy、仓库内容或外部工具写入。记忆内若出现要求忽略规则或调用敏感工具的内容，提示词里的“不要记录某些内容”并不能阻止它影响模型。

建议：明确记忆是数据，不具有覆盖系统/开发者规则或 Host 授权的能力；区分用户有意保存的偏好与项目事实，并在工具层执行最小权限。加入恶意记忆、跨项目注入和工具越权测试。分隔符只是辅助，不是安全边界。

P1当前 Host 预发布版本不在设计的 engines 范围内 方案 198、1115–1118 行

评审时本机 Host 版本为 0.2.2-rc.1，设计 engines 约束为 >=0.2.0-rc.2 <0.2.1-0 || >=0.2.1-rc.1 <0.3.0-0。按 semver 预发布匹配规则，第二段引入的是 0.2.1 这一预发布基线，不自动包含 0.2.2-rc.1；当前插件管理器会阻止不满足 DSH 版本条件的安装/激活。

建议：明确产品要支持的预发布版本并更新 engines 范围；在发布前对每个声明支持的 Host 版本执行实际安装与启动验证，同时对未来不兼容版本继续保持拒绝。

P1npm 发布白名单未包含 Client bundle 方案 1043–1058、1113–1128 行

exports 与 dsh.client 指向 lib/client.js，但 package files 白名单没有 lib。发布的 npm 包将缺少声明的入口，安装后的 UI 加载失败。

建议：将构建产物明确纳入 files/exports，并把 npm pack --dry-run 实际文件清单纳入发布门禁。

中优先级问题

P2配置卡引用的契约与当前宿主不符 方案 828–837、846–872 行

客户端代码使用 configForms.get()/whileServed()，但本机 DSH 当前服务目录中没有 configForms 服务；当前 Settings 表单只面向 volatile 配置，普通配置的修改通常走配置编辑/Loader 生命周期，可能重载插件。文档宣称的普通项“立即生效”因此需要重新验证。

建议：按 engines 中每个受支持版本核对可用服务及可编辑 Config 字段；确定缺少 Settings/Config Editor 时的降级；让生效说明与实际生命周期一致。

P2动态记忆 section 应明确关闭变量插值 方案 576–584 行

systemPrompt section 默认进行 {{variable}} 插值；设计没有要求带用户正文的 section 设 interpolate: false。若正文出现未知或格式不完整的插值标记，可能使 prompt assembly 失败，与“读侧故障不阻断 turn”相冲突。

建议：对记忆正文使用字面文本模式，并用包含大括号、未知变量名和畸形标记的 fixture 验证注入正常。

P2索引和备份扩大敏感正文留存面 方案 698–704、779–785、1185 行

索引条目包含完整 text，备份又保存原文；目前没有规定 stateDir ACL、备份/索引的删除与保留策略。即使记忆源条目被删除，派生副本仍可能继续可读。

建议：评估索引是否只需保存定位信息；对私有目录权限作明确约束，权限不得弱于源文件；定义备份轮转、过期索引回收、卸载后的处理和敏感数据诊断输出边界。

P2原子替换不代表断电后已持久 方案 274、698–704 行

fallback 描述 temp + rename，但没有文件与父目录 fsync/flush 的持久性契约。rename 能提供原子可见性，不等于掉电后数据必然留存；跨平台 API 的保证亦待验证。

建议：明确 durability 层级；若承诺断电持久，补齐平台实现并做 power-loss/崩溃注入测试；否则将产品文案限定为进程运行期的原子可见性与最佳努力恢复。

建议验收顺序

  1. 先定写入协议：明确外部 WorkBuddy 写者不遵守锁时的产品保证；完成 revision/operationId 状态机，再实现写工具。
  2. 先证明恢复正确：对正文提交、记账、整理每个阶段注入崩溃；重启后重试不得重复写、漏写或覆盖后续修改。
  3. 验证隔离和授权：测试双工作区、账号切换、匿名/跨站 HTTP、shell 与路径别名，并测试恶意记忆内容不改变 Host 的工具授权。
  4. 验证发布契约：在声明支持的 DSH 版本矩阵逐个安装；核对 npm 包确实包含 client bundle 与所有运行时文件。
  5. 验证跨平台持久性：Windows/macOS/Linux 覆盖并发写、链接路径、CRLF/LF、进程终止及平台支持范围内的 durability。

评审依据：方案文档、同目录 WorkBuddy 记忆系统逆向报告，以及评审时本机 DSH 0.2.2-rc.1 的 Service/Config 契约。Host 的 live contract 查询确认 systemPrompt AssembleContext 提供 scope/signal、webServer 自定义路由可接 Connection admission/rejection，且当前目录没有 configForms。上述接口检查不代表插件实现或其测试已完成。
