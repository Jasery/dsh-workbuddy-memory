0. 一分钟读懂这份方案

这个插件是干什么的

把 WorkBuddy 的那本 Markdown 记事本，直接递给 DSH 用。两个程序看的是同一本，不留副本、不用同步；谁改了，另一个立刻能看到。

为什么会有一份优化方案：发现另一个插件也在做类似的事，逐项对比之后，看清自己哪些地方还差一口气。下面 11 项，就是「差的那几口气」。

四条底线，用大白话说

  1. 不抄第二本记事本 —— 一旦有两份，就永远说不清哪份才是最新的。
  2. 不每轮多烧一次模型 —— 让模型判断「这轮没啥可记」，本身也要花钱。
  3. 别指望模型一定听话 —— 「请不要这么做」写在说明书里不算保护，代码拦住才算。
  4. 发版必须有人点头 —— 自动检查欢迎，自动发布不行。

5. P0 · 立即处理（3 项）

O-01P0截断改为「结构行保留 + 尾部优先」
背景（大白话）

记忆文件就是一本越写越厚的记事本。每一轮对话，插件都要把这本子递给模型看，但一次只能递固定字数 —— 比如用户记忆最多 8000 字，超了就得裁掉一部分。现在的裁法是「从第一页开始留，把最后几页撕掉」，可偏偏新写的内容都记在最后几页。当初选这个裁法只是因为最好实现，没人把「新内容写在末尾」这件事放在一起想。

现有问题

失效场景：任一 MEMORY.md 超过对应上限（用户级默认 8000 字符，持续记一两个月就会到）→ 模型调 memory_append 写入新结论，落在文件尾部 → 下一轮注入只保留文件开头 → 模型读不到刚刚写进去的内容，可能重复写或给出与文件不符的回答。

同源第二处：memory_read 读大文件或大章节时也用 slice(0, limit) / truncateChars（默认 20000 字符，src/tools/read.js:88/101）。该文件注释记载曾修过「section 分支无视 limit 把整节灌进上下文」，但截断方向仍是头截 —— 工具读取路径同样丢尾部。

触发条件与影响面：文件超限即触发，注入与工具读取两条路径同时失真；render.js:146 只留一行「已截断到 N 字符」提示，不说明丢的是哪一段。项目 11-11 才创建、记忆量还小，所以尚未暴露；按规则持续写就会撞上。对比项目 common/text.mjs:67-69 把同类修复写得很直白：「修 LIFO/FIFO 错配，写了等于没写」。

原因与取舍

失效场景已在「现有问题」展开，这里只讲取舍：不是照搬对方功能，而是让截断方向与写入方向一致；同时保留结构行（# / ## / HTML 注释），因为章节大纲丢失会让模型连「有哪些主题」都看不到。对方把窗口外的中部结构行列在截断标记后且不计预算，这个细节一并吸收。规则块的 hint 必须完整存活，因此不复用同一个函数，只改 base 的截断。

动作
新增 clipForInjection(text, limit)（建议放 src/render.js 内部或 src/fsx.js）：按行处理 → 头部连续结构行无条件保留 → 从尾部向前累积内容行到预算用尽 → 中部结构行按原序列在截断标记后 → 保持 UTF-16 代理对安全（沿用现有 truncateChars 的码元处理）。
单独处理
规则块 render.js:55-60 用 truncateChars(base, room) 给 distillHint 留位置，提示行必须完整存活，不能套用同一个尾部优先函数；保留现有「base 让位、hint 完整」的算法，只把 base 的截断换成结构行感知版本。
回退开关
新增 inject.clipMode: 'tail' | 'head'，默认 tail；CHANGELOG 注明旧行为可用 head 恢复。
验收
tests/render.test.mjs 补 4 例：尾部新条目在超限后仍可见；中部 ## 标题完整；超长中文/emoji 不产生半个代理对；规则块的 hint 不被截断。
O-02P0工具名冲突：可选前缀 + 文档声明
背景（大白话）

插件给模型配了 9 个「按钮」，比如 memory_read（读记忆）。这些名字就像快捷指令，模型的操作说明、README、界面提示里都写死了。麻烦的是另一款同类插件也用了同一个按钮名，按下去干的却不是一回事。当初只按「机器上只装我一个」来设计，没考虑撞名。

现有问题

直接冲突：dsh-memory-palace 也注册 memory_read（src/tools.mjs:221），但参数完全不同 —— 本项目是 target / date / section / sectionsOnly / limit（tools/read.js:22-28），对方是 scope（memory | project | today | yesterday | daily | all）。

触发条件与三种后果：同一 DSH profile 同时装两个插件时 —— ① 后注册者覆盖前者；② 宿主重名校验报错，导致其中一个插件的工具整体不可用；③ 不报错，但模型按错的 schema 传参，调用返回 unknown_target 或空结果。

不止工具层：两边都会写 .workbuddy/memory/MEMORY.md（本项目 CAS 会报 conflict、对方无全局锁），同一文件还会被注入两遍（本项目头截 system prompt + 对方尾截历史投影），用户级记忆分裂成两份。0.1.4 的文档对此只字未提，用户碰到时只能当作「插件坏了」。

为什么不能直接改名：改名会同时破坏现有调用方、i18n 规则文案、README、面板提示和既有测试断言，属于高破坏变更。冲突是「同装时」才发生，所以默认保持原名、只给需要共存的人一个可选前缀。

原因与取舍

取舍集中在「破坏面」：冲突只在同装时发生，而直接改名会破坏现有调用方、注入规则文案、README、面板提示与既有测试断言。因此默认保持原名，只提供 compat.toolPrefix（如 wbm_）给需要共存的用户，并在 README 明确「不建议同 profile 同装」—— 用最小破坏换掉最大风险。

动作
在 registerTools()（src/tools/index.js:120-133）注册前对 tool.name 应用可选前缀；locale/{zh,en}.json 的规则文案按前缀动态生成（避免文案里写死工具名）；新增配置键 compat.toolPrefix（默认 ''）；README 中英各增一节「与其他记忆插件共存」。
验收
默认配置下注册的工具名与 0.1.4 完全一致（回归断言）；设 wbm_ 后 9 个工具全部带前缀且规则文案同步；README 中明确列出 5 条同装风险。
成本来源
前缀要贯穿「工具注册 → 规则文案 → 面板提示 → 测试」，容易漏一处，故列 P0 但排第二。
O-03P0三条软规则升级为硬门禁
背景（大白话）

写记忆这件事本身做得挺稳：同一时刻只让一个人改、改之前先留底稿、改完能一键退回。人在界面上删东西、改整篇，也会先弹窗问一句。但这些保护只管「人点按钮」；如果模型自己决定删一条、重写整篇、把一批旧笔记搬走，目前一路绿灯，全靠说明书上一句「请不要这么做」。

现有问题

预览与执行没有绑定：memory_prune 有 dryRun 默认 true 的计划输出，但 dryRun:false 可以一步执行，模型或面板完全可以在没看过 plan 的情况下归档一整批日期文件。「先蒸馏再归档」只写在工具 description 与 locale/zh.json 里。

不可逆动作无工具层门禁：remove（删条目）、removeSection（整节删除）、replaceDocument（整文件重写）都没有确认步骤；replaceDocument 仅校验 ui.allowFullTextEdit 与 validateDocument()（store.js:166-185），连 expectedRevision 都不强制。

软约束举例：规则里的「conflict 时不要重试覆盖」「不要用 write/edit 直接改记忆文件」「不要把流水原样搬进 MEMORY.md」是自然语言；模型不遵守时，代码里没有第二道闸。

触发条件与影响面：一次误调用即可删掉条目 / 整节 / 整文件，或移走一批日期文件。备份链确实能恢复，但 memory_restore 要用户自己知道去调；面板的冲突弹窗只处理 revision 不匹配，不处理「删错了」。现状不是「没做安全」，而是「写链与面板确认都做了，工具层的不可逆动作还缺一道闸」。

原因与取舍

取舍在于「学到哪一层」：对方用 tools/pre-execute 把 confirm:true 路由到宿主原生 kind:"ask" 弹窗，模型误传也要真人点允许（tools.mjs:456-481），重整还在门禁前后双重复核（hybrid/tools.mjs:36-55/330）—— 这个「不信任模型」的思路值得学。但宿主 API 是否在本项目目标版本 dsh >= 0.2.0 可用需先验证，因此先在工具层做两阶段，不硬依赖宿主弹窗；也只覆盖三类高影响动作，避免每次写记忆多一次往返。

动作 A
删除类（store.js:127-129 的 remove、replaceDocument:166-185、prune:243-302 的非 dryRun 路径）增加两阶段：首次调用返回命中位置/影响条目数与一次性 confirmToken，第二次带 token 才执行；token 与 operationId 幂等台账绑定，过期或路径变化即作废。
动作 B
replaceDocument 强制要求 expectedRevision（目前只校验 allowFullTextEdit），杜绝「整文件覆盖不带版本」。
动作 C
面板 /action（host/routes.js:447）沿用同一 token 机制，不另开后门 —— 与现有「工具和面板共用同一 store」原则一致。
不动的部分
append / edit / replaceSection 保持单阶段，否则每次写记忆都要多一次往返，违背「不加每轮固定成本」。
验收
不带 token 调用删除类一律返回 confirmation_required 且文件 mtime 不变；token 重放第二次返回 duplicate；replaceDocument 缺 revision 返回 revision_required。

6. P1 · 工程加固（4 项）

O-04P1配置键审计与收敛
背景（大白话）

设置页里有一堆开关，大约 30 个。开关越多越容易出问题：有的勾了没反应，有的两个一起打开会互相打架。项目里已经删过一个「骗人」的开关 —— 界面给三个选项，代码其实只认一种。当初是每加一个功能就顺手加一个开关，没定期回头清点。

现有问题

没有「键 → 读取点」清单：新增键只靠人同步三处，漏一处就产生「界面能勾、代码不读」或「代码读了、界面没有」；现有 30 个键也没有逐一验证过是否都有读取点。

组合语义无人校验：readOnly 与 ui.allowWriteActions、inject.enabled 与四个子开关、inject.limits.user 与 distillAbove（后者默认由前者 ×2 推导，改一个必须同步另一个）、ui.allowFullTextEdit 与 ui.allowWriteActions —— 目前只在注释里解释，没有机器校验或文档矩阵。

顺带核实的一处同类字段失真：src/env.js:110 把 USER.md 的文件路径传给 uidFromPersonalDir()，而该函数按 user-<uid>-personal 目录名解析（paths.js:144-148），结果 probe.profile.uid 恒为空串；:122 用了 dirname() 才正确。当前 memory_status 不输出该字段，外部不可见、影响很低，但它正是「字段存在却无效」这一类问题的样本，说明审计有必要。

影响面：不是故障，是维护成本随键数线性增长；对比项目 v1.8.0 一次性删掉三模式与写入总开关，正是因为模式互串已经修不完。

原因与取舍

src/config.js 现有约 30 个可配键（inject / write / guard / ui / search / locale 六组）。项目自己已经踩过一次：config.js:73-77 注释记载 conflictPolicy 提供 fail|merge|overwrite 但没有任何代码读它，设了 overwrite 仍返回 fail，最后删掉 —— 注释原话「一个说谎的开关比没有开关更糟」。对比项目 v1.8.0 一次性删掉三模式与写入总开关，正是同类判断。配置越多，组合语义越容易产生「设了不生效」。

动作
产出一份「键 → 读取点 → 生效时机 → 与其他键是否冲突」清单（可放 docs/implementation-notes.md）；逐个核对哪些键只在 schema 里出现、哪些组合会互相否决（例如 readOnly 与 ui.allowWriteActions、inject.enabled 与四个子开关）；删掉无读取点的键，合并语义重复的键。
兼容
被删键在 normalizeConfig() 里保持「未知键静默失效、绝不抛错」，与现有容错一致；CHANGELOG 明确写出旧值失效，必要时给一版兼容读取 + 警告日志。不学对方 v1.8.4「迁到新文件且不迁移存量值」的硬切法。
验收
清单里每个存活键都能定位到 src/ 下的读取行；删键后旧配置传入不抛异常；tests/index.test.mjs 增加「未知键不破坏装配」用例。
O-05P1会话级状态分桶 + 静默预设工具掩码
背景（大白话）

DSH 是个一直开着的程序，可以同时开好几个窗口、聊好几个项目。插件里那份「最近用过哪些项目」的清单，是全局只此一份，不分哪个窗口。平时够用，但同一个项目开两个窗口，或者用「极简模式」做对照测试时就会别扭：一个窗口刚写完记忆，另一个窗口的缓存被一起清掉；极简模式下还照旧把记忆和 9 个按钮都摆给模型看。

现有问题

粒度问题，不是数据串台：first-turn 模式下，同一工作区的两个会话共享同一个冻结快照；其中一个会话写入后 sections.invalidate() 走的是 frozen.clear()（inject.js:99-104）全清所有键，另一个会话下一轮要重新探测。行为正确，但缓存与失效都做不到按会话管理。

面板视角错位：recent 与项目目录反映的是「宿主见过哪些工作区」，不是「当前标签页属于哪个会话」；右栏页签虽然用 sessionId 解析项目（§14.3），全局总览仍是插件级状态。

裸测环境做不到零足迹：没有计划模式禁写，也没有 silentPresets。在官方 minimal 这类独占 system prompt 的预设下，本项目仍注入 4 段提示词并把 9 个工具 schema 暴露给模型；对比项目用工具掩码把 schema 从模型可见集移除（index.mjs:318-357）。

触发条件与影响面：多会话并行、同一项目开两个会话、或用 minimal 预设跑对照测试时出现。影响主要是 token 与交互体验，不是数据损坏，所以列 P1 而非 P0。

原因与取舍

DSH 是长驻进程，多个会话可能同时工作在不同 cwd。本项目目前靠每次调用时的 probeEnvironment({cwd}) 解析路径，本身不易串台，但 recent（index.js:52-64）与面板状态是插件级单例，冻结快照虽按 cwd 分键、失效却是 clear() 全清。对比项目为此用四张按 sessionId 分桶的 Map，并专门写了 test-planmode-crosstalk / test-settle-cwd / test-session-cwd 三个回归测试；它还让官方 minimal 预设下连 7 个记忆工具的 schema 都从模型可见集移除，做到「零 token 足迹」的裸测环境（index.mjs:318-357）。这类问题只有在长期多会话运行后才暴露，值得提前防。

动作
新增 src/session.js：按 sessionId 保存 cwd / 最近项目 / 冻结快照键；registerSections 与 createProjectCatalog 读取分桶状态。新增 session.silentPresets（默认空，不默认改行为），命中时用宿主工具掩码把写工具从模型可见集移除；判据缺失一律 fail-open（不静默），与对方一致。
前置验证
先在目标 DSH 版本上确认 ctx.tools.restrict / 等价 API 是否可用；不可用则退化为「工具执行时返回 silent 拒绝」，并在文档注明「schema 仍在可见集，非零足迹」。
验收
两个不同 cwd 的会话交替调用，注入块与面板项目列表互不污染；静默预设下写工具调用一律被拒。
O-06P1注入成本核算 + 恒定前缀拆分
背景（大白话）

每轮对话都要把几段文字塞进提示词里，这是要花 token 的。项目已经做了缓存，避免反复读硬盘；也有个状态查询能看到用户记忆有多大、有没有超预算。但「这一轮到底塞了多少字、哪一段被裁掉、比上一轮多花了多少」，查不到 —— 有点像家里有总电表，却看不到每台电器的用电量。

现有问题

度量只覆盖一个文件，且是推断值：status.injected 是 Math.min(userChars, limits.user) 算出来的配置推断，不是本次装配实际拼出的文本长度；project / rules / profile 三块各注入多少字符、是否被截断、丢了多少，全都查不到。也无法回答「这一轮比上一轮多花了多少 token」。

前缀里有一段每轮可能变的内容：规则块尾部挂着随用户记忆大小变化的蒸馏提示，on-change 下每轮重新装配。cache.js 优化的是「不重复读盘」，并没有核算「system prompt 前缀能否命中缓存」；first-turn 与 on-change 的实际代价也没有对照数据。

触发条件与影响面：用户记忆接近或超过 8000 字符、或规则文案改动时最明显。对比项目把最坏注入份数写进 CONFIG.md:64（8 条消息 ≈ 5 万字符），本项目连查询入口都没有，只能靠读代码估算。

明确不是问题的一点：本项目没有采用历史投影，因此不存在对方那种「注入份数随目录数膨胀」的风险。这里要补的是可观测性，不是换通道。

原因与取舍

本项目四个注入块里，rules 块含随用户记忆文件大小变化的 distillHint（render.js:50/115-130），inject.refresh 默认 on-change 每轮重新装配。也就是说 system prompt 前缀里有一段每轮可能变化的内容，而现有度量只覆盖用户级文件大小（status.js:86 的 Math.min(chars, limit) 是推断值），不覆盖实际装配文本。对比项目 projection.mjs:1-32 通篇解释「把易变内容移出 system prompt，前缀缓存才永久有效」，CONFIG.md:64 甚至主动算出最坏注入份数 —— 哪怕它的实现有预览期 API 风险，这种成本意识本身值得学。本项目不需要改成历史投影，只需要把账算清、把恒定与动态拆开。

动作 A
在 memory_status 已有 user.injected 的基础上增加 injectedChars：按四个块返回本次装配的实际字符数、是否被截断、截断丢了多少字符；保留原有推断字段以兼容调用方。
动作 B
把 rules 拆成「恒定规则段」与「动态压力提示段」两个 section（order 相邻），动态段单独返回空串即可被宿主丢弃；这样文件没超限时 system prompt 前缀完全稳定。
动作 C
文档补一份「每轮注入多少字符、哪些段每步在变、first-turn 与 on-change 的缓存代价」对照表，作为后续是否引入投影通道的决策依据。
验收
memory_status 返回值通过 lossless() 校验；规则段在文件未超限时逐字相同；新增测试断言动态段为空时该 section 返回 ''。
O-07P1跨会话 / 并发写入回归测试
背景（大白话）

项目有 14 个测试文件，主要验证「给这个输入，一定得到那个结果」。缺的是另一类：把以前出过的事故重演一遍，确认没再犯 —— 两个窗口同时写同一个文件、同一个操作被重试两次之类。写记忆这条链路是整个插件最不能出错的地方，动它之前最好先把这些场景钉死。

现有问题

缺「事故型」回归：没有以真实故障命名的用例 —— 两个会话不同 cwd 交替装配/写入、两个 writer 并发写同一目标、同一幂等键重试、确认 token 重放，这四类都没有自动化覆盖。现有测试主要断言「函数在给定输入下返回什么」。

已声明的边界没被验证：store.js:8-14 承认的「毫秒级并写可能覆盖」目前只是注释，没有测试钉住「一个成功、一个 conflict / lock_timeout、备份存在且可恢复」这条不变量。

触发条件与影响面：多会话、并发写、客户端重试时出现。写链是整个产品的信任基础，而 O-01（改截断）、O-03（加确认）、O-05（加会话状态）都要动 store / inject / tools；没有回归网，很容易把锁或 CAS 改坏而不自知。对比项目虽然测试框架更弱，却专门有 test-planmode-crosstalk / test-settle-cwd / test-session-cwd 三个串台回归。

原因与取舍

现有 14 个测试文件、4441 行，框架比对方规范（node:test + coverage），但覆盖的是「函数返回对不对」；缺一类「上次出过的 bug 会不会回来」的回归。对比项目虽然只有自研 assert，却专门有 test-planmode-crosstalk.mjs、test-settle-cwd.mjs、test-session-cwd.mjs 三个按真实事故命名的测试。本项目的写链（跨进程锁 + CAS + 备份）是整个产品的信任基础，尤其需要这类测试守住。

动作
新增 tests/session-crosstalk.test.mjs（两个 cwd 交替装配与写入，断言不串项目）、tests/concurrent-write.test.mjs（两个 writer 同时写同一目标，断言一个成功一个 conflict 或 lock_timeout，且备份可恢复）、tests/confirmation.test.mjs（配合 O-03，断言未确认不落盘、token 重放幂等）。
验收
npm test 全绿；npm run test:coverage 的 src/**/*.js 覆盖率不低于改造前基线（先记录一次基线值）。

7. P2 · 排期项（4 项）

O-08P2CI 校验（明确不自动发布）
背景（大白话）

现在发版本全靠手工：改完、跑一遍测试、打标签、发到 npm。没有机器帮忙核对「标签和版本号对不对」，也没一份写下来的发版清单。而且项目有规矩：发版前必须先问过人，不能测完就顺手发出去。所以缺的是「自动帮忙检查」，不是「自动帮忙发布」。

现有问题

没有机器校验：tag 与 package.json.version 是否一致、PR 是否跑过测试、覆盖率是否下降，全靠发版的人手动确认；没有 CI 状态可看。

没有写下来的发布清单：容易在「刚改完、测试也过了」时顺手执行发布，绕过既有确认约定。对比项目的 publish.yml 把版本校验 → build → selftest → 按版本算 dist-tag 串成流水线，前半段值得学，但最后一步是 npm publish --tag 自动发版 —— 照搬会直接违反约定。

触发条件与影响面：每次发版时暴露。不是代码缺陷，是流程风险；一旦漏确认，后果是对外发布不可撤回的版本。

原因与取舍

本项目仓库无 .github/，5 个 release 与 npm 版本靠手工，没有「tag 与 package.json 版本是否一致」的机器校验；对比项目的 publish.yml 把版本校验、构建、selftest、dist-tag 计算串成流水线，这部分值得学。但它的最后一步是 npm publish --tag 自动发版，与项目既有约定（发布前必须人工确认，P-4）冲突，因此刻意只截取前半段：CI 负责校验与产物准备，发布保持人工。

动作
新增 .github/workflows/ci.yml：push / pull_request 触发 → npm test → npm run test:coverage；tag v* 额外校验 tag 与 package.json.version 一致、产出待发布包与 release draft。不包含 npm publish、不创建 Release、不打 tag。这些动作由人工确认后执行，命令写入 docs/implementation-notes.md。
附带
把 awesome-dsh-plugin 收录 PR #14592 的 gate 状态检查纳入文档清单（按已有经验：仓库年龄门槛由 regate.yml 自动重跑，不要推空提交催绿）。
验收
PR 上能看到测试状态；故意制造 tag/version 不一致时 CI 失败；workflow 文件里 grep 不到 npm publish。
O-09P2双门禁重整命令
背景（大白话）

记忆写久了会变厚，得定期压缩。早期做法是把旧流水原样搬进长期记忆，后来发现只会越搬越肿，改成「让模型按主题提炼，再把旧笔记归档」。方向对了，但「什么时候该压、多久能压一次、压之前要不要问人」全写在说明书里，没有任何机器把关。

现有问题

蒸馏完全靠提示词：没有机器校验「文件是否真的超出注入预算」，也没有冷却期。模型可能在同一会话里反复做整文件重写，或为凑数多轮精简 —— 对比项目 v1.8.3-alpha.2 专门修过「agent 多轮精简替换凑数」，可见这不是假想风险。

没有状态记录：没有重整时间戳，无法知道上次重整何时发生；也没有把「用户确认 + 整档备份」与重整动作强制绑定（replaceDocument 会备份，但触发由模型自由决定）。

触发条件与影响面：用户 MEMORY.md 接近或超过 8000 字符、模型读到蒸馏提示时触发。一次不合适的全量重写可能丢结论；备份可恢复，但用户先看到的是「记忆变少了」。这不是缺功能，是已有能力缺门禁。

原因与取舍

本项目现在只给「蒸馏提示」：超过 limits.user 警告部分读不到，超过 distillAbove 要求按主题压缩（render.js:98-130）。全是软约束，也没有冷却期，模型可能反复做整文件重写。对方把重整做成机器门禁（超预算 且 冷却 ≥7 天，pre-execute 与 execute 双重复核，时间戳由机器写、先剥模型自带注释，用户确认弹窗，整档备份 + 失败回滚：hybrid/tools.mjs:36-55/330-354）。本项目已有 replaceDocument 与完整备份链，缺的只是门禁与触发入口，补齐成本可控。

动作
新增一个不与对方同名的工具/命令（建议 wbm_reorganize）：门禁 = 目标文件字符数 > inject.limits.project 且 距上次重整 ≥ reorgCooldownDays（默认 7）；时间戳作为 HTML 注释由机器追加；执行前强制 expectedRevision + 两阶段确认（复用 O-03）；复用 replaceDocument 与备份链，不新开写路径。
不照搬
不做「超预算回显附门禁指引」那类 prompt 补丁，也不允许用户级重整（用户级文件超限应靠 O-01 + 规则提示处理）。
验收
未超预算 / 冷却期内一律拒绝且不落盘；带伪造时间戳的输入会被剥离；重整后 memory_list_revisions 能列出备份并可 memory_restore 回滚。
O-10P2多 buddy 目录只读兼容
背景（大白话）

插件默认去项目的 .workbuddy/memory 找记忆。有些人的工作区用的是 CodeBuddy，记忆放在 .codebuddy/memory，插件就扑空，看起来像没生效。用户级的路径其实已经兼容两种，项目级还没有。当初按「一个项目只该有一个记忆目录」设计，因为多一份就得同步、容易乱 —— 这条底线后面也要守住。

现有问题

兼容缺口：同时使用 CodeBuddy 的工作区，记忆可能落在 .codebuddy/memory/ 而不是 .workbuddy/memory/。此时 memory_status 报「没有项目记忆」、注入为空、写入返回 no_store，用户会以为插件没生效。

切换粒度太粗：要换目录只能改 dataFolderName 或环境变量，是全局切换，做不到「这个工作区用 A、那个工作区用 B」。

触发条件与修法风险：.workbuddy/memory 不存在而 .codebuddy/memory 存在时触发。影响是兼容性而非数据错误；但最自然的修法（把所有已存在目录都写一遍，正是对方 paths.mjs:40-47 的做法）会立刻违反 P-1，产生第二份真源，所以只能扩读取候选。

原因与取舍

对方默认桥接 .workbuddy/memory 与 .codebuddy/memory，本项目 dataFolderName 一次只能指一个名字（src/paths.js:40-45）。对同时使用 CodeBuddy 的工作区，本项目看不到另一侧的记忆，是一个真实的兼容缺口。但对方的做法是「所有已存在目录全部同步写」，会把一条事实复制成两份 —— 直接违反 P-1。所以只扩读取候选，写入目标仍保持单一。

动作
新增 inject.readFolderCandidates（默认 ['.workbuddy']），解析时按优先级挑第一个存在且含 memory/ 的目录作为唯一项目真源；memory_status 显示「发现但未采用的候选目录」及原因。写入继续只用选定目录，绝不双写、绝不主动创建任何 buddy 目录（与 write.ensureLayout 默认 false 保持一致）。
验收
同时存在两个目录时只注入一份；memory_append 只改选定文件；候选清单在 memory_status 中可见。
O-11P2文档：定位说明 + 宿主契约风险清单
背景（大白话）

文档其实不少：两份 README、几份设计稿，还有一本记满「宿主实际行为和文档不一样」的踩坑笔记。但都是给自己人排障用的，没有一段是写给「正在两个插件之间挑一个」的用户看的，也没有一张「升级宿主时该检查哪几处」的清单。这次对话连着问了四轮才把两个插件的关系理清，就是缺这段说明的证据。

现有问题

用户视角会混淆：本次对话连续四轮追问（「是不是只做一次迁移」「也会写 buddy 目录吗」「每轮都写吗」「最大区别是什么」）就是证据 —— 两个插件同处一个类目、同样围绕 MEMORY.md，在插件目录里二选一时只能靠猜，装错了才发现用户级记忆不互通。

风险信息分散：宿主契约的坑散在 implementation-notes 各节与源码注释里；已知限制（对不遵守锁的外部编辑器只能检出已知冲突、毫秒级并写仍可能被覆盖）只写在 store.js:8-14 文件头。升级宿主版本时没有 checklist，容易复现 0.2.0 → 0.2.2-rc.1 那类契约变化。

触发条件与影响面：用户选型、宿主升级、排障时暴露。不改运行时行为、成本最低，所以列 P2；但它是「让人用对」的最后一道，不该一直缺着。

原因与取舍

两个插件同处一个类目、同样围绕 MEMORY.md，用户很容易靠猜二选一 —— 本次对话连续四轮追问（「是不是迁移」「也会写 buddy 吗」「每轮都写吗」）本身就是证据。对比项目把自承限制集中写在 CONFIG.md / DEVELOPMENT.md（最坏注入 8 条 ≈ 5 万字符、pre-step 抛错毁整轮、预览期 API 升级需核对类型声明），这种「把风险摊开写」比漂亮 README 有用。本项目 docs/implementation-notes.md 有类似味道但没成体系。

动作 A
README 中英各增「与 dsh-memory-palace 的区别」：三行讲清「共用文件 vs 自带系统」「显式工具 vs 每轮子代理」「system prompt 四段 vs 历史投影」，并写明不建议同 profile 同装。
动作 B
docs/ 增「注入成本与宿主契约风险」：列出本项目依赖的宿主 API（systemPrompt.section、tools.register/guard、webServer.register、locale、connection.requestRejection）、各自的降级路径、以及升级 DSH 时需要复核的点；补「已知做不到的事」（对不遵守锁的外部编辑器只能检出已知冲突，毫秒级并写仍可能被覆盖）。
验收
README 与 docs 两份文件都被 files 发布清单覆盖或明确标注为仓库内文档；中不出现「自动」「同步」「零成本」等会误导的表述。

8. 明确不做（含原因）

不做的事原因未来若重新评估的前提
每轮自动记忆子代理每轮结算固定一次 LLM 调用，闲聊也要模型回答「无需写入」（SUBAGENT_SYSTEM:38-40）；对方 v1.8.0 删掉本地防闲聊闸门后，过滤成本全压给模型。日志永不过期不删 → 回喂膨胀 → 目录模式 → 更多工具轮次，形成自放大循环先做本地预筛（无工具执行/文件改动/错误信号/用户明确偏好即跳过）或事件触发，默认关闭、强制指定廉价模型，且实测每轮额外 token 可接受
按文件身份的历史投影依赖宿主预览期 API（agent/pre-step、session.surface.eventAt、MessageSourceMap.form）；对方 DEVELOPMENT.md §7.4 自承抛错会毁整轮 turn、契约失效表现为「记忆静默不注入」宿主 API 稳定并进入公开类型声明；且 O-06 的成本核算证明当前 system prompt 方案确实成为瓶颈
用户级真源独立 / 多目录双写直接违反 P-1。对方用户级用 ~/.deepseek-harness/MEMORY.md，WorkBuddy 端改偏好 DSH 端看不到；项目级多目录双写还会导致「dsh 目录旧内容 + buddy 新内容」同时注入无。这是定位差异，不是待优化项
MEMORY.md 去掉全局锁 / 移除写入总开关本项目写链（跨进程锁 → revision → 备份 → 原子写）与 readOnly 是信任基础；对方靠章节 stale 校验，粒度不同无
破坏性变更不迁移存量配置值对方 v1.8.4 把自定义指令迁到新文件且明确不迁移存量值，用户旧配置静默丢失。本项目删键应保持宽容读取 + 明确告知无
一句话边界

这份方案要的是「对方已经踩过坑并验证过的工程判断」，不是「对方有的功能」。11 项里没有一项会引入第二个记忆真源、第二个 LLM 调用或第二个发布路径。

9. 实施批次（按依赖排序，不排工期）

批次包含为什么这样分组批次出口
批次 1O-01、O-02、O-03三项互不依赖；O-01 修既有 bug、O-02 防共存事故、O-03 补安全边界，都是「不做会有实际损失」npm test 全绿；新增断言全部通过；README 共存说明上线
批次 2O-04、O-06、O-07O-04 先收敛配置，避免 O-06 新增 injectedChars 与前缀拆分时又堆键；O-07 为批次 1 的写链改动补回归配置清单可逐键定位读取点；memory_status 可查注入字符数；覆盖率不低于基线
批次 3O-05依赖宿主工具掩码 API 的可用性验证；验证不通过就走「执行时拒绝」的降级实现，不阻塞其他批次跨会话串台测试通过；静默预设行为有文档说明
批次 4O-08、O-11CI 与文档都不改运行时行为，风险最低；文档需要批次 1–3 的最终结论才能写准PR 可见测试状态；workflow 内无自动发布；README/doc 与实现一致
批次 5O-09、O-10O-09 复用 O-03 的确认机制与现有备份链，必须后置；O-10 涉及路径解析，改动面广且收益最低门禁拒绝路径不落盘；多目录场景只注入一份、只写一处

批次顺序只表达依赖关系，不代表时间估算。每项完成后单独提交，便于按 git revert 精确回退。

11. 风险与回退

优化项风险缓解 / 回退
O-01截断方向改变后，模型看到的片段与旧版不同，已有超大文件的「开头内容」不再优先可见inject.clipMode: 'head' 一键回到旧行为；CHANGELOG 写明；结构行始终保留，章节大纲不丢
O-02前缀若漏改某处文案，会出现「规则让模型调 memory_append，实际注册的是 wbm_memory_append」默认前缀为空（零行为变化）；规则文案改为由注册名动态生成；加一条「规则文案中出现的工具名必须存在于注册表」的测试
O-03两阶段确认让删除/归档多一次往返；面板交互要同步改只对三类高影响动作启用；面板与工具共用同一 token，不另开后门；append/edit 保持单阶段
O-04删键后旧 profile 配置里残留未知键normalizeConfig() 保持宽容；必要时保留一版兼容读取 + 警告日志；不做对方那种静默硬切
O-05宿主工具掩码 API 在 dsh 0.2.0 上不可用先验证再实现；不可用则退化为执行时拒绝，并如实说明「非零 token 足迹」
O-06 / O-11新增诊断字段可能触发宿主 lossless JSON 快照校验所有新字段经现有 lossless() 兜底（src/tools/index.js:28-47），不返回 undefined/NaN/-0
O-08CI 被误配成自动发版，绕过人工确认验收里明文 grep 检查；workflow 只校验不发布；发布命令单独写文档
O-09 / O-10重整门禁误判导致该重整时拒绝；只读候选挑错目录门禁状态与候选清单都在 memory_status 可见；每项单独提交，可 git revert
