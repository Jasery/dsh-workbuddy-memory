记忆面板顶部标签：审计与优化方案

范围为项目记忆的注入提示、总览告警和文件头部。同步使用同一注入判定的面板入口。P0 修正口径，P1 收口版面，P2 补细节。

面板顶部那排 .wbm-chip 是记忆面板的“仪表盘”。本稿逐个核对它什么时候亮、亮什么颜色、数字从哪来，并把发现的问题整理成可评审、可验收的两阶段方案。

一分钟读懂

面板顶部有几粒小标签：项目、有记忆、条目、超限、待归档。进了单个项目，标签换成 MEMORY 条数、已用百分比、超注入限额、rev。

它们本来只回答两个问题：有没有事？要不要现在处理？但 0.2.0 起默认分层注入，记忆文件不再整本塞进上下文，只塞“常驻记忆”这一节。文件很大，不代表注入很多；整份文件超过 10000 字，也不再等于“下一轮会被截断”。

可标签的判据还停在分层之前：对已经分层的文件，仍然拿整份文件大小去比 10000，于是 12k 文件配 1k 核心也会亮红字；真正被截断的“核心超预算”，反而没有任何标签。这不是文案问题，是仪表盘指错了表。

另外还有几处小毛病：KB 和“已用 %”用的不是同一个单位；项目超过 50 个时，只有“项目 N”统计了全部，其余四个只统计前 50 行；没有 MEMORY.md 的项目显示“0 条 / 已用 0%”，而左栏写的是“无记忆”；文件头把 KB 塞进了 % 的位置，显示成“18.2 KB%”。

先修告警，再收版面。让面板直接沿用注入端的判定，同时让「需要处理」能打开告警对应的项目。第二阶段把统计合成一行，窄栏保留醒目的告警，并提供键盘可访问的详细说明。

背景：这排标签本来在回答什么

把每个工作区想成一只抽屉，里面的 MEMORY.md 是记事本，日期文件是每天撕下来的便签。记忆面板就是抽屉的查看窗口。

  • 全局总览回答“这台机器上有哪些抽屉、哪些该收拾”。所以顶部是项目数、有记忆的项目数、总条目数、超限项目数、待归档项目数。
  • 项目页签回答“这个抽屉里的本子现在怎么样”。所以顶部是本子的条数、体积、注入占用、版本号。
  • 文件头部回答“我正打开的这一页是什么”。所以是只读 / 追加、条数、版本号。

这排指示灯加进面板时，默认会把整本记事本带进对话，文件大小自然是最容易看的指标。后来改成分层，平时只带常驻页，其余只带目录，需要时再翻。面板依然盯着整本记事本的大小，于是有些灯亮错了。

常驻页能带多少，取决于留给它的空间。标题和提示也要占位置。如果后面的条目放不下，这次对话只能看到前面一部分，文件里的原文仍然可以打开查看。

现状：每个标签的准确含义

所有标签都是 .wbm-chip，颜色只有四种：默认灰（中性）、ok 绿、warn 黄、bad 红。另有一个 accent 蓝色样式，定义了但没有任何地方使用。

P0-1：分层文件被误报超限（最严重）

现在的判定只有一行：memory.chars > limits.project（src/host/catalog.js:177）。它不知道两件事：当前注入模式，以及这个文件有没有分层。而注入端在分层模式下用的是另一套预算：

// src/render.js:112-119（分层文件）
const budget = shareOf(cfg.inject.coreBudget, key === 'project' ? 'project' : 'user')
const core = renderEntries(parsed.coreEntries, `## ${t('coreHeading')}`, Math.max(0, budget - prefix.length), t)
states[key] = core.dropped > 0 ? `layered:core-over-budget(${core.dropped})` : 'layered'

于是出现两种相反的错：

  • 假阳性：一个 12000 字的文件，核心只有 1000 字。整份 12000 > 10000，顶部亮红「超注入限额」，横幅说“下一轮注入会截断”；实际只注入 1000 字核心，完全装得下。
  • 假阴性：一个 9000 字的文件，核心 8000 字。整份 9000 < 10000，顶部什么都不说；实际核心超出约 1390 的预算，会被丢掉一大截。提示词里已经写了 layered:core-over-budget(N)，面板上却看不到。

同一个 overLimit 还喂给了三处：顶部红 chip、项目摘要的红横幅（src/client.js:3720-3722）、总览「需要处理」列表（attention.overLimit）。它们会一起说错。讽刺的是，配置卡自己的说明是对的（src/client.js:211），0.2.0 更新日志也写明“分层模式下 inject.limits.project / .user 只决定这一路源开不开”。

P0-3：单位混用

项目 chip 显示 bytes，百分比却按 chars 算。配置里的 10000 是字符数，不是字节数。中文一个字通常 3 个 UTF-8 字节，所以“18.2 KB”大约只有 6200 字；把 18.2 KB 和限额 10000 放在一起按字节算会得到 182%，而面板写的是 62%，看起来像两套账。文件头更直接：把 humanBytes() 塞进了百分比槽位。

P0-4：总览五个数字的口径不一致

catalog.list() 先为全部项目算统计，再按 ui.maxProjects（默认 50）切片。但 totalsOf() 是对切片后的 rows 求和，只有 projects 被 list.total 覆盖（src/host/routes.js:392）。项目超过 50 个时，就会出现“项目 120 / 有记忆 20 / 条目 400 / 超限 1”，其中后四个只代表前 50 行。

P0-7：30 天边界

标签用 oldestAgeDays > 30（严格大于），归档扫描在 ageInDays(date) < beforeDays 时跳过（src/write/archive.js:84）。整 30 天的有效日期笔记已进入默认归档预览，顶部却不提示。默认值分散在目录统计、面板对话框、/action 的 prune 分支和写入 store 四处。

评审补充的边界

  • 英文项目包装占 20 UTF-16 码元。实测 9,998 码元正文配 10,000 码元限额，full 和分层模式下的 legacy 都发生正文截断。整份渲染先去掉首尾空白，再扣除包装并处理截断提示。限额太小时还可能省略整个块。
  • 实测完整核心块恰好需要 1,400 码元时，单条核心仍可能因预留溢出提示位置而未注入。渲染器的 dropped 记录最终未注入条数。
  • 目录统计最多读取 256 KiB，注入端最多读取 2 MiB 并拒绝截断快照。目录只解析前缀时，可能漏掉后面的核心标题或第二个同名核心。
  • 「需要处理」目前只读已显示的项目，最多列 6 项。只把顶部改成全量统计时，唯一超限项目排在第 51 位就会出现「超限 1」和「没有需要处理的项目」并存。项目列表的百分比、项目摘要和文件横幅也各有旧判定或旧文案。

P1-8 到 P1-14：语义与版面

  • 有记忆：hasMemory 只判断文件存在；空文件、读失败的文件都算。绿色 ok 让“存在”看起来像“健康”。
  • 条目：countDocumentEntries 只用 parseSections()（从 H2 起算），漏掉第一个 H2 之前的 bullet；而详情页在 0.2.2 已经用 topSection() 把 (top) 算进去了。同一个文件，总览说 0 条，详情页有内容。
  • rev：16 位十六进制来自 contentRevision()（src/write/fslock.js:35）。它是写入冲突令牌，不是健康指标；放在顶部既占宽又无解释。
  • 窄页签：右栏页签固定按 layout: 'wide' 渲染（src/client.js:3870），CSS 只在 820px 以下隐藏左栏，不收缩 chip（src/client.js:1125-1133）。最多四个 chip 加标题、项目名、刷新按钮，在 360px 左右会换两三行。
  • crumb：总览标题永远是“记忆 · 全部项目”；点选项目只影响正文，于是会出现“全部项目”crumb 和“全部项目”按钮并排。
  • 首帧：state 为 null 时 totals 取默认全 0，chip 先渲染 0，再被数据替换。
  • 源关闭：ratio() 在 limit 为 0 时返回 {percent: 0, level: 'none'}，chip 仍显示「已用 0%」。

目标形态

原则五条：

  1. 面板沿用注入端的判定。总览、项目列表、项目摘要和文件打开后的提示对同一状态使用一致文案。
  2. 每个项目的同一预算问题只显示一个注入状态。总览保留汇总数量，并提供打开相关项目的入口。
  3. 文件长度和注入限额使用相同的 UTF-16 码元。详情可另列磁盘字节数。
  4. 中性统计用灰色，警示颜色配具体状态文字。
  5. 右栏页签保留条数和最值得关注的注入状态。详细原因可通过键盘打开。

项目记忆的注入状态

面板依据当前文件和配置计算预计注入结果。状态按下表从上到下匹配。注入总开关、项目开关、项目限额和文件读取结果都参与判定。

条件判定标签
确认文件不存在未创建未创建
总开关关闭、项目开关关闭，或 limits.project = 0已关闭，超限统计为否注入已关闭
已读取完整文件，正文为空白无内容可注入文件为空
不可读、读取时文件变化，或超过注入读取上限未测得注入占用，单独显示原因无法测量
layered 且文件已分层复用核心渲染的 dropped。标题、项目包装和溢出提示预留都计入预算核心可完整注入，或「核心超预算 · N 条未注入」
full 任意文件，或 layered 下的 legacy复用整份渲染的处理结果，区分完整、正文截断、限额太小导致整块省略已用 X%、超注入限额，或「限额过小 · 未注入」

分层项目默认分到 1,400 UTF-16 码元（总预算 4,000 的 35%）。整份文件大于该份额时，主题仍然可以按需读取。只有 dropped > 0 才触发核心超预算告警。详情可分别列出完整核心块所需空间、实际注入量和预算，便于解释提示预留造成的边界结果。

整份模式的占用率使用包含标题的完整块所需空间除以限额，截断判定来自渲染结果。占用率接近或等于 100% 可以提示接近上限，红色只在正文确实被截断或整块无法注入时出现。

版面规则

  • 宽面板显示标题、面包屑、一行中性统计、告警和刷新。截短信息的完整内容可通过键盘访问。
  • 项目顶部显示文件统计和一个有效注入状态。右栏页签缩短为条数和状态，例如「核心 3 条未注入」。项目名可省略，告警文字保持可见。
  • 总览选中项目后，面包屑显示项目名并提供一个明确的返回入口。
  • 项目列表仍有展示上限。「需要处理」从全量异常中单独取有上限的项目预览，可打开左侧列表以外的项目。超过预览上限时，显示未展示数量并提供查看入口。
  • 首帧保留加载状态。加载完成且项目总数为 0 时，显示「暂无项目」，用户记忆和画像入口仍可见。

视觉与无障碍

  • 检查宽面板、常规右栏和 360px 右栏的标题、统计、告警与刷新按钮。
  • 用键盘打开、阅读和关闭详细说明，并验证关闭后焦点回到触发入口。读屏能读出告警状态及原因。
  • 告警始终有可见文字。验证深浅主题和中英文文案。

原因与取舍

  • 分层项目的主题正文按需读取。整份文件超出核心分配空间是常态，告警依据实际有无核心条目未注入。
  • lastAssembly.states 记录当前会话上次装配。面板的预计状态覆盖全部项目，使用当前磁盘与配置。使用 first-turn 的会话可能继续沿用上次装配，面板避免承诺「下一轮一定截断」。
  • overLimit 可以从新状态生成，供现有调用者过渡。新版面板使用带原因的注入状态，区分核心条目未注入、整份截断、限额过小和无法测量。
  • 注入与面板读取共用上限和完整性判断。轮询仅在文件身份变化时重新解析，配置变化直接用缓存的解析元数据重新计算。
  • 30 天阈值表示默认归档预览的时间范围，恰好 30 天的有效笔记应进入候选。手动调整预览天数时，该阈值仍用于全局告警。
  • 口径修复可单独验收注入与告警是否一致。版面调整随后用宽窄栏截图和键盘操作验收。
  • 完整 revision 仍可在冲突弹层查看。项目与文件顶部腾出它占用的空间，写入时继续使用同一令牌。

不做的事

  • 不自动拆分 / 重排记忆文件；分层仍然是用户确认后的动作。
  • 不改 coreBudget、limits 的默认值，也不改注入算法。
  • 不新增配置项；30 天先做成共享常量，等确实需要可调再升格。
  • 不做“点 chip 筛选项目”的交互（可以放进 P2 以后单独评估）。
  • 不改记忆文件格式，不发布、不打 tag、不合并 main。
