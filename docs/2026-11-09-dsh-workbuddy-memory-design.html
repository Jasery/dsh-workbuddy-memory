dsh-workbuddy-memory · 通用插件方案

WorkBuddy 与 DSH 共用一套记忆文件：文件即真相，两侧都能读能写，谁都不产生第二份副本。

通用插件 · 可发布 零第三方记忆依赖 装完即用 engines.dsh >=0.2.0-rc.2 零运行时依赖 含 Web 界面 2026-11-09

一句话：这是一个独立记忆层，不是某个记忆框架的适配器。它把 WorkBuddy 的三层记忆文件当成唯一真相，往 DSH 的 system prompt 里注入，用自带工具往里面写，用跨进程锁和内容哈希保证两个客户端不会互相覆盖。

它不建立在任何记忆框架之上：不引入外部记忆存储，不需要额外的策略配置，不依赖第二套索引或加密服务。注入、写入、检索、整理、诊断五件事全部由插件自己实现，只使用宿主提供的 systemPrompt 与 tools 两个服务。

  1. 格式不改，位置不改，语义不改。一旦改了文件布局，WorkBuddy 就读不到这些记忆，「打通」立刻退化成「各写各的」。插件的所有自由度都在「怎么读写」上，不在「存在哪、长什么样」上。
  2. 不制造第二份真相。正文永远只存在 .workbuddy/memory/；插件私有目录只放索引、备份、幂等表、小节基线这类派生数据。删掉 ~/.dsh/workbuddy-memory 不丢任何记忆。
  3. 写侧失败优先于写侧成功。两侧可能同时改同一个文件，冲突时宁可让模型重读重试，也不能覆盖对方刚写的内容。默认 conflictPolicy: fail，合并是显式选项。
  4. 读侧永不阻断。没有 WorkBuddy、没有目录、文件损坏、权限不足，一律降级为空注入，宿主照常跑完这一轮。
  5. 通用插件的验收标准是「别人装得上、跑得动、出错能自查」，不是「我这儿能用」。所以有跨平台路径、能力探测、memory_status 自检、中英 locale、完整 npm 元数据。
  6. 注入走 section，不走 runtime context。DSH 的 ctx.systemPrompt.context() 会物化成 user 角色快照写进历史；记忆是稳定前缀，放那里会随每次变化重复消耗 token。
  7. 界面是入口，不是第二条写入路径。面板里的编辑、整理与回滚，和会话里调用工具走同一个 write()——同一把锁、同一套栅栏、同一份备份、同一张幂等表。UI 只负责把参数填好；人比模型多出的权限只有两项：不受幂等表约束、可以选择先备份再覆盖。

一、定位

1.1 是什么 / 不是什么

维度是不是
角色DSH 的一等记忆层：装完就有记忆，不需要再配策略、Provider、图数据库不是任何记忆框架的适配器，也不是某个上层功能的附属组件
数据WorkBuddy 的三层 Markdown 文件（项目 / 用户 / 画像）不是自建数据库、不是向量库、不是云端 API
写入工具化写入，带幂等、栅栏、合并、备份不靠提示词让模型「自觉调 Edit」
生命周期会话首轮注入，会话内冻结不是每轮 recall，不是语义检索驱动
边界只管「WorkBuddy 这套文件怎么被 DSH 读写」不管自动提炼、跨会话图谱、skill 自进化

1.2 自包含设计

插件的每一项能力都必须能自己解释来源。除了宿主必然提供的两个服务，其余全部用 Node 标准库实现，不引入记忆框架、数据库、向量库或任何第三方运行时依赖：

能力由谁提供为什么这样选
注入ctx.systemPrompt.section宿主唯一稳定的前缀入口，不必自己拼提示词
工具与守卫ctx.tools.register / .guardschema 自动进入 prompt 组装，守卫是不可绕过的写入闸门
原子写 / 文件锁node:fs + 自带 fallbacktemp + rename 与 wx 锁各 30 行，自己写比引库更可控
版本与幂等node:crypto sha256内容哈希即可表达「是不是同一版」，不需要版本号服务
检索自带增量索引（JSON）记忆体量在 MB 以内，子串检索足够
配置schemasteryDSH 官方 schema 库，配置可校验、可给默认值
界面（可选）ctx.slots + 宿主的 React组件必须与宿主同一 React 实例，所以 React 走 peer，不自带、不打包
验收方式：CI 加一条「最小化环境」用例——在只装官方核心包的 profile 上加载本插件，跑完整读写流程。任何未声明的隐式依赖都会在这条用例里暴露。

二、通用性设计

「通用」不是形容词，是 8 条可验收的硬指标。每条都对应具体代码位置，做不到就不叫通用：

01
零硬依赖
peerDependencies 只有 @deepseek-ai/cordis 与 @deepseek-ai/dsh-tools（宿主必然提供）。schemastery 走 dependencies 自带一份；dsh-atomic-write 动态 import，拿不到就用自带 60 行 fallback，不报错。
02
能力自足
注入 / 写入 / 检索 / 整理 / 诊断五件套闭环。任何一个能力被关掉，其余四个照常工作；全开时也不依赖外部插件补齐。
03
环境自适应
启动时探测 WorkBuddy 的存在形态（完整 / 只有全局 / 只有项目 / 没有），按结果决定注入哪些块、开放哪些写入目标。memory_status 把探测结果原样吐给用户，排障不用猜。
04
跨平台
路径全走 os.homedir() + path.join，不出现盘符字面量；EOL 按文件探测并原样写回；原子写在 Windows 上重试 EBUSY/EACCES；锁用 wx + PID 存活检测，不依赖 POSIX flock。
05
不制造第二份真相
正文只写 .workbuddy/。私有目录放索引、备份、幂等表、小节基线；删掉它只影响性能，不影响数据完整性。
06
可发布
完整 npm 元数据（engines.node / engines.dsh / files 白名单 / dsh.bundle.patch）、中英 locale、MIT LICENSE、README 双语、无个人路径与凭据。
07
可配置可关闭
每个能力独立开关（inject / write / search / guard / ui），而且都能在界面里改，不必手编 YAML。关了 UI 只剩工具链，功能不缺。
08
失败不阻断宿主
读侧任何异常→空注入；写侧任何不确定→失败并给出下一步；插件 apply() 本身不抛错（配置非法时降级为默认值 + 警告日志）。

三、「打通」的语义

3.1 文件即唯一真相

两侧之间不存在「同步」。它们读写的是同一批文件，所以「打通」= 同一份数据被两个客户端看见。这意味着：

  • 不需要同步服务、后台任务、冲突队列；
  • 不需要迁移脚本，DSH 装上当天就能看到 WorkBuddy 里全部历史记忆；
  • 不会有「两边不一致」的状态，只会有「谁先谁后」的时间问题。

3.2 三个方向的流动

图 1 · 三条路径全部落在文件上。插件唯一需要工程化的是右侧那条「写」路径。

3.3 一致性与时间窗

「打通」是最终一致，不是实时一致。不同方向的时间窗差得很远，必须写进 README，否则用户会以为坏了：

路径可见延迟原因
WorkBuddy 写 → DSH 读下一次装配（on-change）或下一个会话（first-turn）取决于冻结策略
DSH 写 → 本会话读立即工具写完主动刷新快照
DSH 写 → WorkBuddy 读WorkBuddy 下一个会话WorkBuddy 也是首轮注入，已加载的会话不重读
DSH 写 → 画像WorkBuddy 下次蒸馏（小时到天）蒸馏器是独立任务，插件不触发
DSH 写 → 另一个 DSH 会话那个会话的下一轮各自持有快照，不共享内存状态

3.4 三档冲突策略

冲突的定义：写入前重读文件，发现内容哈希与调用方提供的 expectedRevision 不一致。按 conflictPolicy 处理：

策略行为适用
fail（默认）不写。返回 conflict + 当前 revision + 变化小节清单，模型重读后重试一次通用默认。安全，代价是多一次往返
merge小节级三方合并（见 7.4）。只在「双方改的不是同一个小节」时成功，否则仍返回 conflict两侧频繁交替写入时开
overwrite先备份，然后覆盖只在脚本化批量导入时用，默认禁用
为什么默认不是 merge：合并需要 base（上一次读到的版本），而 base 只对「本插件读过的文件」存在。用户刚在 WorkBuddy 里改过、DSH 侧还没读过，此时 base 已经过期，强行合并会得出错误结论。所以只有 base 能链到磁盘的上一个已知版本时才允许合并，否则退回 fail。

5.2 插件骨架

// src/index.js
import z from '@deepseek-ai/schemastery'
import { resolveConfig } from './config.js'
import { detectEnvironment } from './env/capabilities.js'
import { createSnapshotStore } from './inject/snapshot.js'
import { registerSections } from './inject/sections.js'
import { registerTools } from './tools/index.js'
import { registerWriteGuard } from './write/guard-tool.js'

export const name = 'dsh-workbuddy-memory'
export const inject = ['systemPrompt', 'tools']
export const Config = z.object({ /* 见第十二节 */ })

export function apply(ctx, config) {
  let cfg
  try { cfg = resolveConfig(config) }
  catch (error) {
    // 配置非法也不打断宿主：降级为只读默认值
    ctx.logger?.warn?.('[workbuddy-memory] bad config, fallback to read-only', error)
    cfg = resolveConfig({})
  }

  const env = detectEnvironment(cfg)          // 同步探测，不抛错
  const store = createSnapshotStore(cfg, env)

  if (cfg.inject.enabled && env.hasAnyMemory) registerSections(ctx, cfg, store)
  if (cfg.write.enabled && env.writable.length > 0) registerTools(ctx, cfg, store, env)
  if (cfg.guard.enabled) registerWriteGuard(ctx, cfg, env)
}

5.3 工具守卫：拦住裸写

DSH 自带的 write / edit 能直接改 .workbuddy/memory/MEMORY.md，绕过所有栅栏。通用插件必须堵住这条旁路，否则安全链是纸做的：

// src/write/guard-tool.js
const BARE_WRITERS = new Set(['write', 'edit', 'str_replace_editor'])

export function registerWriteGuard(ctx, cfg, env) {
  ctx.effect(() => ctx.tools.guard((exec) => {
    if (!BARE_WRITERS.has(exec.name)) return
    const target = exec.arguments?.file_path ?? exec.arguments?.path
    if (typeof target !== 'string') return
    if (!env.isMemoryPath(target)) return
    return `${target} 是 WorkBuddy 记忆文件，请改用 memory_append / memory_edit；` +
           `直接写入会绕过版本栅栏与备份，可能覆盖另一个客户端刚写的内容。`
  }))
}

守卫只拦「记忆目录内的写入」，不拦读取，也不拦 memory_* 自己的写入路径。确实要手工改，可以关掉 guard.enabled。

规则块的路径是动态生成的——不能假设用户在哪个盘、用哪个数据目录名。规则块里出现真实绝对路径，模型才知道往哪写：

// 规则块骨架（最终 1.2 KB 以内）
## 记忆写入规则（WorkBuddy 兼容层）

- 项目长期笔记：`{projectMemoryPath}` —— 用 `memory_edit` 改小节，用 `memory_append` 追加条目。
- 每日流水：`{dailyPath}`（当天日期）—— append-only，永不覆盖。
- 用户级长期记忆：`{userMemoryPath}` —— 仅当用户明确要求跨项目长期记住时写。
- 蒸馏画像：只读。`USER.md` / `SOUL.md`：不写。

写什么：建改应用、修 bug、写报告、重构、选定技术方案、用户分享项目约定。
不写什么：搜索结果、临时路径、工具报错、命令清单、原始输出、任何密钥。

写失败返回 `conflict` 表示文件被另一个客户端改过：`memory_read` 重读后重试一次，
仍失败就如实报告，不要用 write/edit 强行覆盖。

6.2 限额与冻结

块默认上限（字符）超限处理
项目10,000截断 + **ACTION REQUIRED**：先读全文，再用 memory_consolidate 合并过期条目
用户4,000截断 + 提示
画像2,000截断 + 提示

截断按 UTF-16 处理，末位落在代理对中间时回退一位——否则切出半个 emoji，部分模型网关直接 400：

export function truncateUtf16(text, limit) {
  if (text.length <= limit) return { text, truncated: false }
  let end = limit
  const code = text.charCodeAt(end - 1)
  if (code >= 0xd800 && code <= 0xdbff) end -= 1   // 高位代理，切开会坏
  return { text: text.slice(0, end), truncated: true }
}

冻结策略

1
key = assembly.scope
WeakMap 按会话隔离，会话结束自动回收，不写清理逻辑。
2
first-turn
首次装配读盘并冻结，之后直接返回缓存字符串。文本逐字节不变 → system 节点不动 → 前缀缓存全命中。适合只用 DSH 的场景。
3
on-change（默认）
每次装配比对 mtimeMs + size，变了重建。代价是一次前缀失效，收益是 WorkBuddy 刚写的记忆下一轮就能看到——跨客户端协作场景需要这个。
4
写后主动失效
本插件工具写完立即刷新快照，不依赖策略，保证「同 turn 写完即可读」。

七、写入管线

7.1 工具集

工具参数要点返回

target 是枚举不是路径字符串——不接受任意路径，直接堵死 ../ 与 _memory.md。

7.2 安全链

图 3 · 4→5 的顺序不能颠倒：先取锁再复检，否则复检与提交之间存在窗口。界面发起的写入走的是同一条链，只是调用方从工具变成 /action。

7.3 幂等与栅栏

幂等键 = sha256(target + '\0' + section + '\0' + normalize(text))，normalize 只做去首尾空白、空白折叠、全角标点转半角。命中返回 { ok: true, duplicate: true }——对模型来说「本来就在里面」就是成功。

幂等表是 append-only JSONL，超过 5,000 行裁剪到 2,000 行，只服务短窗口去重，不做永久账本。

栅栏用内容哈希，因为项目文件没有版本号：

比较含义动作
expected === current幂等重放ok: true, skipped: true，不写
expected !== current被别的写入者改过走 conflictPolicy
未传 expectedrequireExpectedRevision: false 才允许直接写（后写者胜），默认拒绝

与 WorkBuddy 的 Version: N 单调版本不同，内容哈希只表达「是不是同一版」，不表达先后。这个语义差异必须写进 README。

同 turn 放行

一个 turn 内连续两次写会改变 revision，第二次若拿旧值提交会误判冲突。处理：按 scope 记录「最近 3 秒内本插件自己提交的 revision」，提交时命中即放行。不用 hook、不依赖 turn 边界事件。

7.4 小节级合并

conflictPolicy: merge 时的算法，粒度是小节而不是整文件：

1
取三份
base（上次见到的版本，存在 base/<hash>.json）、ours（本次准备写的结果）、theirs（磁盘当前内容）。
2
按小节比哈希
每个 ## 标题 一段，各自算 sha1 前 8 位。
3
三方判定
theirs == base → 用 ours（只有我们改了）；ours == base → 用 theirs（只有对方改了）；ours == theirs → 无所谓；三者互不相等 → 冲突。
4
任一小节冲突则整体失败
返回冲突小节名，让模型决定放弃还是重读。不做「自动择一」——那等于替用户删内容。
5
顺序
保留 theirs 的小节顺序，新增小节追加到末尾，不重排、不格式化、不动空行。

八、检索与整理

项设计
索引位置~/.dsh/workbuddy-memory/index/<sha256(cwd)[:16]>.json，按工作区隔离
条目{ path, date, section, heading, text, mtime, size }，一个小节一条
增量扫目录比对 mtime+size，只重解析变化的文件
大文件超过 256 KB 只索引标题与首 64 KB
匹配子串（大小写不敏感）优先；中文按 2-gram OR 命中排序
过滤scope（project / user）、from/to（按日期文件名）、section
返回top N（默认 8），正文永远从磁盘现读，索引只用于定位

整理（memory_consolidate）：把 beforeDays 之前的日期文件按主题聚成候选条目，默认 dryRun 只出计划。执行时走同一套安全链逐条 memory_append，全部成功后才删除源日期条目；任一条失败则用备份回滚。

九、交互界面

工具链解决「模型怎么读写」，界面解决「人怎么看、怎么调」。三块界面各自绑定一个 DSH 已有的插槽，全部可关：关掉之后工具链完整可用，只是少了可视入口。

9.1 三个入口

界面宿主插槽解决什么只读降级
配置卡plugins.bundle.config（key = dsh-workbuddy-memory）改限额、开关、冲突策略，不用手编 cordis.patch.yml关掉后只能改 YAML
记忆面板sidebar.panellist + main（keyed）看有哪些记忆、多大、哪条过期、有没有冲突与备份关掉后用 memory_status / memory_search
面板内操作面板内的按钮与内联编辑改条目、加条目、删条目、整理、回滚、跳到源文件ui.readOnly: true 隐藏全部写操作

注册形态参考宿主自带的上下文面板（同样的 inject 声明感知写法，替换包先加载后加载都生效）：

// src/client/index.js —— 客户端入口
export const name = 'dsh-workbuddy-memory'
export const inject = ['slots', 'locale']

export function apply(ctx) {
  const t = ctx.locale.bind('dsh-workbuddy-memory')
  const id = 'dsh-workbuddy-memory'

  // 主面板：keyed slot，key 与侧栏条目的 id 相同
  ctx.effect(() => ctx.slots.inject('main', () => ctx.slots.register(
    { name: 'main', key: id, locale: id },
    MemoryPanel,
  )))

  // 侧栏图标入口：list slot，id / order / label
  ctx.slots.inject('sidebar.panellist', () => ctx.slots.register(
    { name: 'sidebar.panellist', id, order: 24, label: () => t('panel.title'), locale: id },
    SidebarIcon,
  ))

  // 插件配置卡：只有 Host 真的服务该命名空间时才出现，避免空壳页面
  ctx.inject(['configForms'], (scoped) => {
    const forms = scoped.configForms
    if (typeof forms?.get !== 'function') return
    scoped.effect(() => forms.whileServed([id], () =>
      scoped.slots.inject('plugins.bundle.config', () => scoped.slots.register(
        { name: 'plugins.bundle.config', key: id, locale: id, inject: { form: forms.get(id) } },
        SettingsCard,
      ))))
  })
}
界面不是第二条写入路径。面板里的「整理」「回滚」和在会话里调用工具，最终都进同一个 write() 函数——同一把锁、同一套内容栅栏、同一份备份、同一张幂等表。UI 只是把参数填好，不绕过任何一步。

9.2 配置卡：改配置不用编 YAML

配置卡直接绑定 Host 的条目配置（ctx.configForms.get('dsh-workbuddy-memory')），改完写回 cordis.patch.yml 的 config。表单分五组，每组只暴露有意义的键，路径类放在「高级」并默认折叠。

分组控件键
注入开关 + 三档下拉 + 三个数字inject.enabled、refresh、limits.{project,user,profile}
写入开关 + 策略下拉 + 两个数字write.enabled、conflictPolicy、backupKeep、lockWaitMs
检索开关 + 数字search.enabled、maxResults
界面开关 + 三档ui.enabled、ui.panel（sidebar / settings-only / off）
高级只读展示 + 覆盖按钮globalDir、dataFolderName、stateDir、ensureLayout

每一项都显示四件事：当前值、默认值、来源、生效方式。第四项是本设计刻意加的——用户改完最常问的就是「现在生效了吗」：

配置生效方式原因
inject.enabled / 各块开关立即section 常驻注册，provider 内部判定开关，返回空字符串时段落被宿主丢弃
inject.refresh / limits / sanitizePaths立即provider 每次装配读当前配置
write.* / search.*立即工具执行期读配置
ui.*刷新页面客户端组件生命周期，改完由配置卡提示「刷新生效」
globalDir / dataFolderName重载插件路径在 apply() 期解析并缓存，改动后需要重新探测

写入用 mutate 一次提交一组改动，避免「改三个字段产生三次 revision 冲突」。表单带草稿：Host 侧 revision 变了，草稿保留并提示「磁盘上的配置已被其他窗口修改」，由用户决定覆盖还是丢弃。恢复默认走 unset，删除覆盖值而不是写入默认值——这样以后升级默认值仍能跟随。

9.3 记忆面板：看和整理

图 4 · 面板三段式：状态条看占比，树看结构，详情看条目。整与回滚都走预览确认。

状态条

9.4 直接编辑记忆

模型写错了措辞、记了一条不该记的、或者用户自己想起来一件事要补上——这些都不该逼人去命令行改文件。编辑能力按「改动范围」分三层，默认只开最安全的一层：

层交互改动范围默认落到哪个动作
L1 条目点一行变成输入框，Enter 保存 / Esc 取消；行尾出现删除图标单条 - …，其他行逐字节不动开memory_edit（replace / remove）
L2 小节小节标题右侧「编辑小节」→ 整段 textarea → 保存该 ## 小节 内全部条目开小节级替换，其余小节不动
L3 全文工具栏「源码模式」→ 整文件 textarea + 行号整个文件关（ui.allowFullTextEdit）整文件写，保存前做结构校验

一次编辑的完整流程

1
进入编辑态时锁定 revision
面板记住当前文件的 revision（内容 sha256）与该条目的行号范围。不锁文件，只记下「我看到的是这一版」。
2
本地草稿
输入即草稿，不自动保存。失焦不提交，避免误触改坏。未保存时切换节点会提示「有未保存的修改」。
3
保存：POST /action {type:'edit', …}
带 expectedRevision、target、section、from（原文本）、to（新文本）。进同一个 write()：加锁 → 锁内二次哈希 → 备份 → 原子写。
4
成功
行闪一次高亮、状态条刷新、生成一个备份点，右上角出现「撤销」入口（保 10 秒）。提示「已保存，下一轮对话生效」。
5
冲突
二次哈希不符：不写。弹三选一 —— 重新加载（丢弃草稿）/ 看差异（我的 vs 磁盘）/ 覆盖（先备份再写）。默认聚焦「重新加载」。

三个边界

边界规则为什么
画像不可编辑只读，但提供「复制到项目记忆」——把画像里某条搬进 MEMORY.md画像是 WorkBuddy 蒸馏产物，外部写入会被下一次蒸馏覆盖，改了也留不住
限额不阻止人保存成功后若超限额，显示红条 + 「注入会截断」，允许保存工具是「模型建议」，拦得住；人是「决定」，只能提示不能替人否决
结构必须合法L3 保存前校验：标题树完整、代码围栏成对、无 _memory.md 重名非法结构会让 WorkBuddy 解析器掉进退化分支，整份记忆失效
人工编辑与工具写入的差异，只有两点：一是人工编辑不受幂等表约束（同一个词被有意写两次也允许），二是人工编辑可以选择「先备份再覆盖」越过栅栏。其余全部相同——同锁、同备份、同原子写、同日志。不要为 UI 另开一条写路径，那等于给自己留后门。

9.5 数据通道

面板的数据来自宿主进程，客户端通过插件自己注册的 HTTP 路由取，不碰内部 RPC 协议（它需要构建期生成绑定，第三方插件用不了）：

// src/ui/routes.js —— Host 侧
const BASE = '/dsh-workbuddy-memory'

export function registerRoutes(ctx, cfg, store, env) {
  const off = [
    ctx.webServer.register({ kind: 'exact', path: `${BASE}/state`, handler: stateHandler }),
    ctx.webServer.register({ kind: 'exact', path: `${BASE}/content`, handler: contentHandler }),
    ctx.webServer.register({ kind: 'exact', path: `${BASE}/action`, handler: actionHandler }),
  ]
  return () => off.forEach((dispose) => dispose())
}
路由方法返回 / 入参约束
/stateGET环境探测结果、三来源字节与限额、条目数、冲突、备份列表、生效配置只读；响应上限 64 KB
/contentGETtarget / date / section（全部枚举，不接受路径）只读；单文件上限 512 KB，超出返回头部 + 截断标记
/actionPOST{ type: 'edit' | 'consolidate' | 'restore', expectedRevision, dryRun, ... }必须带 revision；进同一个 write()；只有 dryRun 可免 revision

刷新策略：面板可见时 3 秒轮询 /state，document.hidden 时暂停，任何写操作完成后立即拉一次。不用推送——宿主的广播接口不在已公开的类型里，靠它会把可用性押在未承诺的行为上。

路由安全边界：/action 只接受枚举动作，不接受任意路径、不接受 shell、不接受「删除文件」。edit 的 from / to 只是小节内的文本片段，永远不参与路径拼接。它是 Git 意义上的「写」，不是「执行」——不提供任何能跑命令的入口。所有动作写日志，来源标记为 ui，与会话内工具调用可区分。

9.7 界面部分怎么分期

期内容验收
M4a 配置卡五组表单 + 来源与生效方式展示 + 草稿冲突改限额后不重启，下一次装配即按新值截断

十、能力探测与降级

通用插件不能假设「用户已经装好 WorkBuddy 并且配置正确」。启动时做一次同步探测，结果决定行为：

探测结果注入写入目标用户看到
项目 + 全局都存在四块项目 / 全局 / 日期完整能力
只有全局（~/.workbuddy）用户 + 画像 + 规则全局 / 日期（需 ensureLayout）项目块为空，其余正常
只有项目目录项目 + 规则项目 / 日期用户块为空
都没有不注册任何 section拒绝，除非 ensureLayout: true插件静默待命，memory_status 说明原因
目录存在但不可写正常注入只读模式，写工具返回 read_only能读不能写，原因写在返回值里
文件损坏 / 非法 UTF-8该块降级或跳过写入前先备份，用合法内容替换memory_status 标红该文件

ensureLayout 默认 false：不主动创建 .workbuddy 目录。凭空多出一个隐藏目录会让用户困惑，也可能与 WorkBuddy 自己的工作区初始化撞车。真要在纯 DSH 环境里用这套记忆，显式打开即可。

12.1 配置只有一个真相

界面配置卡不维护自己的存储——它写回的就是 cordis.patch.yml 里的那份 config。理由和记忆文件一样：两份配置一定会漂移，最后没人知道哪份在生效。

层来源UI 能改吗
1代码内置默认值不能（改它是改代码）
2环境变量 WORKBUDDY_CONFIG_DIR / WORKBUDDY_DATA_FOLDER_NAME不能（只影响两个路径键，优先级高于配置文件）
3profile 的 cordis.patch.yml → config能，配置卡写的就是这层

memory_status 与面板的状态条都会输出「当前值 + 来源」，四个来源分别标 default / env / config / ui。用户排查「为什么设置没生效」时不用猜优先级。

十三、失败模式

场景行为用户可见
WorkBuddy 未安装不注册 section，工具报 no_storememory_status 说明原因与开启方式
目录不可写只读模式写工具返回 read_only
文件被占用（Windows）原子写内部重试，超时后 busy提示稍后重试
锁等待超时lock_timeout，不写同上
revision 冲突按 conflictPolicyconflict + 变化小节清单
人工编辑时文件被改不写，弹「重新加载 / 看差异 / 覆盖」草稿保留，默认聚焦重新加载
L3 全文结构非法拒绝保存高亮出错行（围栏未闭合 / 标题层级断裂）
人工编辑后超限额保存成功 + 红条提示「下次注入会截断」，不阻止人写
幂等命中ok, duplicate视为成功
写入后超限额写成功 + warning下次注入触发 ACTION REQUIRED
日期文件结构无法识别拒绝写入（不覆盖）unrecognized_target + 文件头部预览
画像解析失败退化到正则，丢 version画像仍注入
索引损坏删除重建首次搜索慢一点
裸写被守卫拦截拒绝并给出替代工具模型改用 memory_*
方向相反的降级：读侧任何异常都降级为「不注入」，绝不阻断 turn；写侧任何不确定都失败，绝不猜。读错的代价是少一点上下文，写错的代价是丢用户数据。

十五、里程碑

阶段交付验收
M0 骨架package / patch / config / locate / capabilities / locale / 日志；先只打点装到纯净 profile 不报错；打点确认 assembly.scope 与 assembly.variables.cwd；memory_status 能输出六种环境矩阵
M1 注入四块渲染、限额截断、脱敏、快照与三种 refresh新会话第一轮看到项目记忆；同会话第二轮 section 文本不变
M2 工具read / search / append / edit + 锁 / 栅栏 / 备份 / 幂等 + 裸写守卫并发与双客户端测试通过；冲突返回 conflict 不覆盖
M3 整理与自检memory_consolidate、memory_status、备份恢复30 天前的日期文件能生成计划并安全执行
M4 界面配置卡 → 只读面板 → 直接编辑 → 整理与全文（见 9.7 四档）改配置不重启即生效；面板与 memory_status 数据一致；UI 写入与工具共用安全链
M5 发布README 双语、locale 完整、三平台 round-trip、client bundle 构建入仓、打包体积达标一条命令装上即可工作，侧栏出现记忆入口

十六、风险与待验证

项状态处置
assembly.scope 是否稳定对应会话未验证M0 打点；不稳定则退化为 cwd + Map + TTL
assembly.variables.cwd 在 section provider 里是否已填充未验证M0 打点；备选 ctx.get('session') 或 process.cwd()
ctx.tools.guard 能否拦住内置 write/edit未验证M2 实测；拦不住就退化为规则块强提示
dsh-atomic-write 在第三方插件里的解析可用性本机可用，其他环境未知动态 import + 自带 fallback，两条路径都要测
ctx.fs 能否写 ~/.workbuddy受限不用 ctx.fs，直接 node:fs，避免沙箱策略差异
WorkBuddy 未来改格式或限额中风险限额全配置化；解析器对未知小节宽容；README 标注基线版本
两侧高频交替写中建议 conflictPolicy: merge；文档说明最终一致时间窗
四块注入挤占上下文低总上限约 17K 字符，接近上限可逐块关闭
模型不遵守规则块、不调工具中规则块祈使句 + 守卫拦截 + 冲突文案引导重试
client 侧 slot 名或 configForms 契约变化中风险client 入口逐项做能力检测（typeof 判断），缺哪个就不注册对应界面，Host 侧不受影响
ctx.webServer 在 headless / ACP profile 不存在待验证按可选服务处理：缺失则不注册路由，面板显示「当前环境不支持界面」
React 版本与宿主不一致低打包时 external，只依赖宿主单实例；不 pin 具体小版本
面板轮询带来额外开销低3 秒间隔、只读 /state（走 statSync 缓存）、页面隐藏时暂停
人工编辑选「覆盖」丢掉对方刚写的内容中覆盖前强制生成备份点；面板顶部「历史」可一键回滚到 5 分钟前
L3 全文编辑破坏结构中默认关闭；开启后保存前校验标题树与围栏配对，非法即拒绝

核心取舍：不做同步、不做自己的存储、不做记忆提炼。只做一件事——让同一批 Markdown 文件被两个客户端安全地读写。

通用性体现在三个地方：装谁的环境都能跑（能力探测）、单独装上就能活（零依赖）、出问题能自己查（memory_status）。这三条做到了才配叫通用插件；只在自己机器上跑通的那是脚本。

基于 WorkBuddy 5.9.3 记忆系统逆向报告（2026-11-06）与本机 dsh 0.2.0-rc.2 的接口实测。
DSH 接口签名取自 @deepseek-ai/dsh 包内 .d.ts；依赖声明范式参考已发布插件的通用写法。
