总评

工具链的并发与安全骨架是可靠的（跨进程锁、revision 栅栏、原子替换、写前备份、操作账本、裸写守卫），但Markdown 结构层只认「一行一个 bullet」。凡是跨行条目，memory_edit 会返回 ok: true 而把文件改脏——这是最坏的一类失败：调用方看到成功，无从察觉。

除 P0-1 外，还有 3 处「静默」行为（换行被原样写入、section 名打错自动建节、同名节只改第一个）与 2 处契约空转（conflictPolicy 无人读、蒸馏提示在 8000–16000 区间不触发）。这些都不影响正常路径，但会在批量整理记忆时集中爆发。

本版已复核并修复：全部 15 条主结论实测成立；其中 6 处子结论/改法经复测发现有问题，已在下文逐条更正（标 已更正），并按更正后的方案落地了 12 项修复（标 已修复）。

二、P0 · 会静默改脏文件

P0-1多行条目只处理首行，续行留成孤儿实测src/markdown.js:12, 154, 216, 244, 320

BULLET = /^([ \t]*)([-*])([ \t]+)(\S.*)$/ 是单行正则，editEntry / editEntryAt 以「一行」为条目边界。带缩进续行的条目（本仓库记忆文件里很常见）因此被拆开处理。

实测（真实工具调用）：
原文件第 5–7 行：- 多行条目首行，用于实测 / 续行一 / 续行二
memory_edit（replace 首行）→ {"ok": true, "replaced": 1} → 结果第 5–7 行变成 - 多行条目首行（已改写） / 续行一 / 续行二（续行原封不动）
再 memory_edit（remove）→ {"ok": true} → 文件只剩 续行一 / 续行二 两行裸缩进文本，且此后任何工具都无法定位它们。

后果：一次「压缩记忆」的批量操作，会在文件里留下一堆没有归属的缩进行。它们不会被 memory_search 当条目返回，也不会被 memory_edit 删除，只能手工编辑或整文件覆盖。

改法：在 markdown.js 增加条目跨度解析，把「bullet 行 + 其后连续的缩进行」视为一个整体，替换与删除都以跨度为单位。初版补丁不完整下面的实现是本版采用的版本，与初版相比多处理了两种真实存在的形态（见本节末）。

/**
 * 一个条目的跨度：[首行, 末尾续行]。
 *
 * 终止条件（保守）：
 *  - 标题一律终止；
 *  - 同级或更浅的 bullet 是新条目；
 *  - 比自身更深的 bullet 是子条目，保留；
 *  - 空行只有在「下一行仍缩进」时才保留（否则它是两条之间的分隔）；
 *  - 其他情况终止。
 */
export function entrySpan(lines, index) {
  const match = BULLET.exec(lines[index].replace(/\r?\n$/, ''))
  if (!match) return null
  const baseIndent = indentWidth(match[1])
  let end = index
  for (let cursor = index + 1; cursor < lines.length; cursor += 1) {
    const next = lines[cursor].replace(/\r?\n$/, '')
    if (HEADING.test(next)) break
    if (!next.trim()) {
      const after = (lines[cursor + 1] ?? '').replace(/\r?\n$/, '')
      if (after === '' || HEADING.test(after)) break
      if (!/^([ \t]{2,}|\t)/.test(after) && indentWidth(BULLET.exec(after)?.[1] ?? '') <= baseIndent) break
      end = cursor
      continue
    }
    const child = BULLET.exec(next)
    if (child) { if (indentWidth(child[1]) > baseIndent) { end = cursor; continue } break }
    if (/^([ \t]{2,}|\t)/.test(next)) { end = cursor; continue }
    break
  }
  return { start: index, end }
}

然后 editEntry / editEntryAt 的 remove 分支 splice 整个 [start, end]；replace 分支用新内容替换整个跨度。editEntry 的候选行判定也要改：命中续行时不能报 not_an_entry，而应回溯到所属条目的首行（见 P1-1）。

初版补丁的两处遗漏（实测）
把初版 entrySpan 原样实现后跑真实文件，两种形态仍然漏：
① 续行中间夹空行：- head / para one / 空行 / para two → span 只到 para one，para two 仍成孤儿（空行被当成终止）。
② 缩进的子 bullet：- parent / - child → - child 命中 BULLET 直接终止，span 只有首行。本仓库 .workbuddy/memory/2026-11-09.md 有 8 行这种嵌套子条目，2026-11-10.md 有 33 行纯缩进续行。

测试：新增用例覆盖「replace 多行条目 → 续行消失」「remove 多行条目 → 无残留」「续行里的文字作为 match → 命中整条」「续行中间的空行」「嵌套子条目归属父条目」。

P0-2replacement / text 中的换行被原样写入，一次调用写多条实测src/markdown.js:111, 216

rewriteBulletBody 只做 trim() 与去掉行首 - ，不检查内部换行；appendToSection 直接拼 `- ${line.trim()}`。两者都会把调用方文本里的换行原样落进文件。

实测（memory_append，text = "一条文本里带换行\n- 伪装成的第二条\n- 第三条"）→ {"ok": true}，文件多出三行：
- 一条文本里带换行 / - 伪装成的第二条 / - 第三条

已更正：漏了一处，且漏掉的那处更危险初版只定位 markdown.js:111, 216，但日期笔记走的是另一条拼接路径（store.js:530 的 `- ${text}`），完全没有防护。实测往日期文件 append：

memory_append（target: project-daily，text 含换行）→ {"ok": true} → 文件变成：
- 第一行 / ## 伪造的标题 / - 伪造条目
不只是多出条目——凭空造出了一个 section，且 parseSections 会认它。MEMORY.md 那条路径只是多条目，这条能改结构；而日期文件是纯追加，事后无法撤销。

后果：「一次调用一条」的契约不成立。模型若把多行文本误当一条传入，会静默产生多条条目——包括伪造出调用方并未显式声明的条目。这与 P0-1 的修法相关：修好后应明确区分「replacement 里的续行」与「新增条目」。

改法（按初版选项 A，并补上漏掉的路径）：入口处拒绝。两个写入点都要管，且要在 store 层统一判定，避免以后再漏第三条路径：

// store.append 入口，一处覆盖 MEMORY.md 与日期笔记
const text = String(input.text ?? '').trim()
if (!text) return fail('empty_text')
if (/\r?\n/.test(text)) return fail('multiline_text', { hint: 'pass one line per call; call again for another entry' })

// markdown.appendToSection 自身再防一层
if (/\r?\n/.test(raw)) return { ok: false, text, created: false, reason: 'multiline_text' }

选 A 更符合工具「一次一条」的语义。replacement 则相反：它替换的是已存在的那一条，所以换行应当作为同一条的续行写入（缩进对齐、去掉行首 marker），否则 - 会被读成伪造的新条目。

三、P1 · 静默失败或契约不成立

P1-1续行本身不可寻址，工具无法收尾实测已更正src/markdown.js:253-269

对续行文本做 memory_edit（match: "续行一"）返回 {"ok": false, "code": "not_an_entry"}。not_an_entry 的语义是「文本存在但不可按条目修改」——设计上是对的，但它意味着 P0-1 造成的残行没有任何工具路径可清理。P0-1 修好后此条自然消解。

已更正：初版两处说法不准确

① 「此后任何工具都无法定位它们」过强。实测 memory_search 能搜到孤儿续行并返回行号：

memory_search("续行一") → {"files":1,"hits":[{"line":3,"section":"甲节","text":"续行一（孤儿）"}]}

准确说法是「能看见、改不掉、删不掉」——而不是连定位都做不到。

② 「not_an_entry 在设计上是对的」这个评价可以更进一层。命中续行时返回 not_an_entry 其实丢掉了调用方最需要的信息：文本确实存在，而且它属于上一条条目。更好的行为是回溯到所属条目的首行并据此修改（本版采用），而不是让调用方自己去猜。

本版实现：continuationOwner(lines, index) 向上回溯到条目首行；editEntry 命中续行时把该条目加入候选集，只有真正落在段落文字上才报 not_an_entry。

P1-2同名 section 只认第一个，改第二个静默 no_match实测src/markdown.js:97-101

findSection 用 Array.find 返回首个匹配。文档里出现两个 ## 同名 时（合并、复制粘贴、多客户端各建一节都会造成）：

实测：对第二个 ## 同名 下的条目执行 memory_edit → {"ok": false, "code": "no_match"}；memory_append 则把新条目追加进第一个同名节（第 5 行），而不是调用方看到的那一节。

后果：用户/模型看着第二节的内容去改，得到 no_match（或写进了另一节），且没有任何提示说「这个标题重复了」。

改法：findSection 增加唯一性检查，返回 { section, duplicates: n }；工具层在 duplicates > 1 时返回 ambiguous_section 并附行号列表，让调用方改用行号定位。memory_read 的 section 列表也应标出重复标题。

已更正：初版给的绕过方案是无效的
初版写「让调用方改用行号定位（editEntryAt 已支持）」。实测不行：
editEntryAt(dup, '同名', 6) → {"reason": "stale_line", "replaced": 0}
因为 findSection 返回第一个同名节（line:0, endLine:3），而第 6 行 6 > 3，直接判 stale_line。同名节的存在恰好把行号这条退路也堵死了——这两条缺陷是同一个根因，初版把它们当成了两个独立问题。

本版实现：resolveSectionAt(text, heading, line) 先用「哪个同名节包含这一行」消歧，只有都不包含时才退回 resolveSection。这样行号既是消歧手段，也保持原有错误码语义。

P1-3section 名打错时 memory_append 静默新建节实测src/markdown.js:116-120

实测：memory_append 传 section: "测试节（打错字）" → {"ok": true, "created": true}，文件末尾长出 ## 测试节（打错字） 新节，条目落在里面。

memory_edit 在同样情况下返回 no_section（拒绝），两个工具行为不一致。自动建节本身是有用的能力（第一次写某个主题时），问题在于无法区分「有意新建」与「拼错」，而 created: true 太容易被调用方忽略。

改法：把新建变成显式意图。两个选项：
A. 加参数 createSection?: boolean（默认 false），未显式要求时返回 no_section 并附最接近的现有标题（编辑距离或前缀匹配），如 {"code":"no_section","suggest":["测试节"]}；
B. 保持自动建节，但返回值把 created 升级为一等状态，并在 locale 规则里提醒模型核对拼写。
推荐 A：默认路径更安全，需要建节时一次调用就能说明。

P1-4expectedRevision 可选，漏传即跳过并发校验代码阅读src/tools/write.js:23, 59 · src/write/store.js:583

两个写工具的 expectedRevision 都只是普通可选参数；writeEverywhere 里是 if (expectedRevision && expectedRevision !== before)——不传就整段 CAS 跳过。而 locale 规则第 4 条明确要求「改已有条目之前先 memory_read 拿 revision」。契约靠规则文本维持，工具层不强制。

后果：模型忘记传 revision 时不会报错，多客户端并发下会静默覆盖——这正是 revision 栅栏想防的事。

改法：按操作类型分档。memory_edit（改已有内容，破坏性）要求必传，缺失返回 revision_required；memory_append（纯追加，可容忍）保持可选。restore 已经是必传（store.js:220），可作范式。若担心破坏兼容，加配置 write.requireRevision: true 并在工具描述里明示。

P1-5H1 下的顶层条目不可达，且无任何节可追加实测src/markdown.js:63

parseSections 只把 match[1].length >= 2（L2–L6）当 section，H1 不算。因此 H1 与第一个 H2 之间的 bullet 属于「无节孤儿」：

实测：文档 # 标题 + - 顶层条目 alpha → parseSections 只返回 ["节"]；editEntry(h1, '标题', '顶层条目 alpha') → no_section。

影响面：用户手工写的记忆文件、以及 WorkBuddy 自己可能生成的结构，都会出现 H1 下直接挂条目的形态。这些条目能注入、能读、能被 search 命中，但改不了也删不掉。

改法：让 H1 也成为可寻址的 section（parseSections 收 level ≥1，但渲染/面板仍可只展示 L2+），或在 findSection 找不到时回落到「文档头部伪节」（heading: '' 或 '(top)'）。前者改动更小，注意 SECTION_ORDER 与面板分段渲染不要因此多出一层。

已更正：初版推荐的前者（选项 A）会让情况变坏
把过滤条件放宽到 level >= 1 实跑，H1 吞掉整个文档：
标题 level:1 line:0 endLine:10（全文件）· 甲节 level:2 line:4 endLine:7 · 乙节 level:2 line:8 endLine:10
因为 H1 比所有 H2 都浅，按现有回溯算法它永远不被关闭。后果是 appendToSection(text,'标题',…) 会把条目追加到文件末尾（乙节之后），而 editEntry(text,'标题',…) 能匹配到所有子节的条目。初版只提醒「面板分段渲染不要多一层」，没看出这个。

本版实现（采用初版的选项 B，伪节）：parseSections 不动，新增 topSection(text) 返回 H1 与首个 H2 之间的区域，heading: '(top)'、line: -1（让 line + 1 === 0 与其它 section 的遍历逻辑对齐）。寻址支持两种写法：显式 section: "(top)"，或直接用文件自己的 H1 标题——后者是人真正会输入的。只有该区域确实含 bullet 时才返回，空头部仍然是 no_section。

P1-6空/纯空白 section 名会造出畸形标题实测src/markdown.js:111-120 · src/write/store.js:39, 543

memory_append 不传 section 时落到 DEFAULT_SECTION = 'Notes'（中英混排文件里凭空多一个英文节）；传纯空白字符串（" "，truthy 但不是有效标题）时，appendToSection 会写出 ## 这样的空标题行。

实测（直接调用）：appendToSection(text, '', 'x') → 结果含 ## 空标题行，created: true。

改法：工具入口对 section 做 trim() 后判空；为空时要么拒绝（section_required），要么明确用 DEFAULT_SECTION 并在返回值里带上 section: 'Notes' 让调用方看见。同时 appendToSection 自身也应对空白标题防御（返回 { ok:false, reason:'empty_heading' }），别只靠上层。

本版实现：三层都做。①appendToSection 自身对空白标题返回 empty_heading，对空正文返回 empty_text；②store.append 先 trim() 再判，空白节名走同一错误码；③不传 section 时仍回落到 Notes（不拒绝），但把落点显式回传：append 的返回体新增 section 字段，调用方能看见自己写进了哪一节，而不是靠读文件猜。

选「回落 + 回传」而不是「拒绝」：Notes 是已声明的默认节，拒绝会让「不想分类、先记一条」这个正常用法失败；真正的问题是落点不可见，回传字段就解决了。

四、P2 · 能力缺口与空转配置

P2-1write.conflictPolicy 是死开关代码阅读已更正src/config.js:74, 205

配置声明了 'fail' | 'merge' | 'overwrite'，全仓仅 config.js 两行引用（声明 + 归一化），没有任何运行时读取点。用户把它改成 overwrite 依然是 fail 语义。

已更正：初版多说了半句初版称「配置卡上的选项实际无效」。实测 client.js 里 conflictPolicy / backupKeep / lockWaitMs 一个字都没有（grep 全空）：配置卡只有 readOnly、home、dataFolder、注入四项、三个开关、面板六项、刷新间隔、maxProjects。配置卡上压根没有这个控件，只能改 YAML。所以准确的表述是「YAML 里能改但无效果」，而不是「配置卡上能改但无效果」。

改法：二选一。要么实现（merge 至少需要三方合并或逐节重试，成本不低），要么从 Config 里删掉，只留 fail 并把语义写进文档。留一个能改但无效果的开关，比没有这个开关更糟。

本版实现：删除。CONFLICT_POLICIES、schema 声明与归一化三处一并移除，config.js 留注释说明为何没有这个键。overwrite 的能力并未消失——它在能被理解的地方存在：面板的冲突对话框会 delete payload.expectedRevision 后重发，即一次显式的「覆盖」点击。配置里那个看不见效果的开关，才是该删的东西。

P2-2蒸馏提示在 8000–16000 区间完全不触发代码阅读src/render.js:114-120 · src/config.js:147 · locale/zh.json:15

distillHint 只在 chars > distillAbove（默认 16000 = 上限 8000 的两倍）时才追加提示；而注入本身在 limits.user = 8000 处截断。文件处于 8000–16000 之间时，超过一半内容读不到，而蒸馏提示不会出现。本次审计的起因就是这个区间——文件 15504 字符，正好卡在空档里。

已更正：初版写作「规则里却一句提示都没有」，是夸大注入块被截断时有提示，只是它不在规则块里、也不是蒸馏提示：

renderFileBlock 在 kept.length < body.length 时追加 _（内容超限，已截断到 8000 字符）_。
缺的是蒸馏提示（distillHint 在 11165 字符、阈值 16000 时确实返回 ''），不是完全没有信号。

附带发现：那条截断文案的单位本身是错的locale/zh.json 原文写「已截断到 {limit} 字节」，而 truncateChars 数的是字符，limits.user 的说明也写「字符」。中文下 8000 字符 ≈ 24000 字节，差 3 倍。这条比 P2-2 本身更容易误导人，本版一并修正。

改法：把提示拆成两档。chars > limits.user 时给「已超注入上限、部分内容读不到」的警告；chars > distillAbove 时给「按主题蒸馏」的强提示。memory_status 已有 overLimit / distillDue 两个独立字段，渲染层对齐即可。

本版实现：distillHint 先判 chars > limits.user → 新文案 overLimitHint（说明「超出部分本会话读不到」并附当前蒸馏阈值），否则再判 chars > distillAbove → 原 distillOverLimit。实测三个尺寸区间：6143 字符无提示、11351 字符触发 overLimit、20279 字符触发 overLimit（超上限优先于蒸馏档）。没有采用初版建议的「把 distillAbove 默认改成等于 limits.user」——那会让「已超上限」与「该蒸馏」两个不同强度的信号混为一档，而 memory_status 早就把它们分开报了。

P2-3备份只保留 5 份，批量整理的回滚窗口很短实测src/write/store.js:484

backupKeep 默认 5，每次写前备份、超出即轮转删除。实测连续 9 次 memory_edit 后，最早的 4 份备份已不存在，无法回到第一次编辑之前的状态。

后果：记忆整理天然是「连续多次小改」，恰好是最需要回滚的场景，却最容易把回滚点用光。

改法：①把默认值提到 20–30（备份是纯文本，几十 KB 成本可忽略）；②或对同一文件同一会话内的连续写入做「批量事务」；③在 memory_status 里暴露当前可用备份数与最早可回滚点，让调用方知道窗口有多大。

本版实现：①，backupKeep 默认 5 → 20。实测同样的 9 次编辑，修复后 9 份备份全在，且仍能读到 - e0（第一次编辑前的状态）。②未做——它需要跨调用的会话概念，而 store 是无状态的；③未做，但 memory_list_revisions 工具补上了「有哪些备份可回滚」这个信息（见 P2-4）。

说明：这条严格说是默认值取舍而非缺陷——「保留 5 份」就是保留 5 份的意思。但记忆整理天然是连续小改，5 份确实过短，值得调；故列为「已修复」而非「报告有误」。

P2-4工具能力严格小于面板能力，整节重写与回滚模型调不到代码阅读src/write/store.js:27, 140-230 · src/tools/index.js:122-124

面板 /action 的 ACTIONS 含 replace-section / replace-document / remove-section / restore，全部走同一条写链（锁 + CAS + 备份 + 账本）。模型侧只注册了 append / edit / prune，整节重写和回滚到某备份都够不着。

后果：模型要做「把这一节从 9 条压缩成 4 条」这类操作时，只能用 9 次 memory_edit + 4 次 memory_append，既慢又不断消耗备份窗口（见 P2-3），且中途失败会留下半成品。本次审计中，我最终只能「手工备份 + 整文件覆盖」，正是绕过了这个缺口。

改法：新增 memory_replace_section（对应 store.replaceSection，已有 validateDocument 级别的校验）与 memory_restore（对应 store.restore，强制 expectedRevision）。store 层两个方法都已实现，只是没暴露成工具——这是投入产出比最高的一条。若要保守，可用配置门控（默认关），并在描述里写清「整节替换会丢弃该节其他条目」。

已更正：「两者都已实现且有测试」——测试这半句错
restore 确实有正向测试（store.test.mjs:249，含「被替换的版本也变成备份」）。但 replaceSectionBody / removeSection / replaceDocument 没有任何正向单元测试：markdown.test.mjs 里 grep 为零，e2e 里那两处 replace-section / replace-document 断言的是拒绝路径（too_large → 413）。这三条面板动作从没被「成功写进去」验证过。
这反而加强了本条的论点：暴露成工具之前得先补测试，而不是「已有测试，直接暴露」。

本版实现（先补测试，再暴露）：先为 replaceSection / removeSection 补正向用例（含「只改本节、其余字节不变」「拒绝非条目正文」「接受续行形态」），再注册三个工具：

  • memory_replace_section：整节重写，validateDocument 级别校验，拒绝标题与段落；
  • memory_list_revisions：列出可回滚的备份。初版漏了这一环——memory_restore 要传备份文件名，而调用方无从猜出文件名；面板有 /revisions 路由，模型侧原本没有对应工具，两者配套才可用。
  • memory_restore：强制 expectedRevision（宿主 schema 层 required: true，缺失时在参数校验就拒绝，比 store 层更早）。

三个工具由 ui.allowWriteActions 门控，与面板一致。

P2-5memory_prune 只覆盖项目日期笔记；用户记忆没有归档通道代码阅读src/write/store.js:243-302

prune 硬编码 target: 'project-daily'，只移动 probe.project.dir 下的 YYYY-MM-DD.md。user-memory（也就是最需要瘦身、且真正被注入的那份）没有任何归档/分卷机制，只能靠逐条改写。

附带一处小问题：ageInDays（src/env.js:149）把文件名日期按 T00:00:00Z 解析，与 localDateStamp() 的本地时区不一致，跨时区时「30 天」边界会偏几个小时。

改法：①prune 支持 target: 'user-memory'，语义不是归档文件而是「按主题拆卷」——把旧结论移到 ~/.workbuddy/memory/archive/YYYY-MM-DD.md，MEMORY.md 只留蒸馏后的条目；②ageInDays 与 localDateStamp 统一用本地零点。

本版实现：②已修；①未做。

②实测确认了偏差：本地 00:30（UTC+8）时，ageInDays('2026-10-14') 返回 29 而非 30，即「30 天」边界提前一天到达，beforeDays: 30 会归档一个实际只有 29 天的笔记。修复后两端都按本地零点计算，且拒绝日历上不存在的日期（2026-02-31 → null，而不是滚到 3 月）。

①未做，因为语义没定：把 user-memory 的旧结论「移到 archive」与「MEMORY.md 只留蒸馏后的条目」这两件事，前者是机械移动、后者需要模型判断哪些结论仍成立——后者不是 prune 该做的（现有 prune 的文档明确写着「只搬流水，不写 MEMORY.md」，正是为了不让工具替模型做判断）。这条需要先有设计，不宜顺手实现。

P2-6memory_search 的默认 scope 与静默截断实测src/tools/search.js:39-40, 48, 70

三个小问题，都会被误读成「记忆里没有这条」：

  • 默认 scope: 'project'。实测在项目无记忆时，memory_search("chrome-use") 返回 {"files": 0, "hits": []}；加 scope: "user" 才命中。而模型最常搜的恰恰是用户记忆。
  • 文件级截断不报告：readTextSafe(..., maxBytes: indexMaxFileBytes)（默认 256 KB）超限时静默截断，落在截断点之后的条目搜不到，返回里没有 truncatedFiles 之类的信号。
  • truncated 语义混淆：返回的 truncated 指「命中数达到 limit」，与文件截断无关，字段名容易被理解反。

改法：①默认改 all，或至少在返回里列出实际扫描的文件与 scope；②文件被截断时在返回里加 truncatedFiles: [{file, bytes, limit}]；③把命中截断字段改名 hitsTruncated，并在 hits.length >= limit 时给 hint。

本版实现：②③ + 部分①。返回体新增 scope、truncatedFiles、hitsTruncated（truncated 保留为别名，避免破坏既有调用方）；files === 0 时给 hint 指明「本工作区没有项目记忆，改用 scope:"user" 或 "all"」。默认 scope 保持 project——参数描述里本就写明了默认值，改默认会改变既有语义，属产品决定而非缺陷。

这条的三个子问题要分开评价：文件级静默截断是真缺陷（已修）；字段名歧义是可用性问题（已修）；默认 scope 是已声明的产品选择（保留）。

P2-7memory_read 的 section 模式忽略 limit代码阅读src/tools/read.js:67-78, 80-81

整文件模式会按 limit（默认 20000）截断并附提示，但 section 模式直接返回 file.text.slice(match.start, match.end)，完全不看 limit。一节内容异常膨胀时（正是需要整理的那种），一次 read 就会把整节灌进上下文。

改法：section 分支复用同一套 truncateChars + 提示；或者显式在描述里写明「section 模式不截断」，让调用方自己控制。前者更一致。

本版实现：前者。实测 limit:100 读一个 8308 字符的小节，修复后返回 truncated: true 且内容被截到百字符量级。顺带修了同分支的一个相邻问题：section 名匹配原本只做大小写归一，同名节时静默取第一个，现在返回 ambiguous_section 并附行号（与 P1-2 同一套语义）。

// P0-1：remove 首行后，续行是否成为孤儿
